## 目标

用户对协调助手说一个目标（先在桌面，之后在飞书 / Telegram），协调助手提出一份带依赖的计划；用户确认后，调度器把子任务派给不同执行器上的专业助手（例如 Codex 开发、Claude 测试、文档助手写说明），每个写入型子任务在自己的 worktree 里做，交付后由服务重跑检查，最后协调助手汇总回到发起的地方。用户只做两件事：确认计划、处理审批和验收。

退出条件（路线图 P3）：至少两个执行器完成「开发 → 测试 → 汇总」；依赖失败、审批超时、取消、冲突与重启恢复都有验证；实际可用性以本机安装和账户权限为准。

### 0. P3-00 先做的三个实验

开工前一天内能定下来，结果决定 P3-02 的能力检查和 P3-03 的做法：

- **按会话注入 MCP**：Codex app-server 能否在 `thread/start` 时带上一个只属于这次 Run 的 MCP 服务器（stdio 命令 + 参数 + 环境变量），而不改用户的全局 `config.toml`；Claude CLI 用 `--mcp-config` + `--strict-mcp-config` 是否只加载我们给的那一份。各跑一次短对话。
- **只读与目录限制实测**：独立 worktree 只把各助手的改动分开，本身不限制进程能写到哪里。对每个执行器的每种配置（Codex 的 `read-only` / `workspace-write` 沙箱与可写根目录；Claude 的禁用写文件工具和 Bash、权限规则、宿主审批拦截），让助手分别用文件工具、Shell 和 MCP 工具往三类路径各写一次：worktree 外（含数据根和用户仓库的主工作区）、worktree 内交付范围以外的目录、交付范围以内的目录，记录哪些写入确实被挡住。结果写进能力检查：只有实测通过的「执行器 + 配置」组合才能承接只读角色；目录限制只有实测能强制时才算隔离，否则在界面上标为「交付范围」，由验收闸门事后核对，不当作隔离。
- **Claude 桌面版能否看到会话**（顺带一次短对话）：用 PalDock 建一个 Claude 会话，看 Claude 桌面版能否列出、能否接着聊；只记录结果，不影响接入方式。
- **Claude 最低版本**：P0 测的是 2.1.325，Mac 测试机上是 2.1.185。确认 stream-json 双向流、`--permission-prompt-tool stdio`、`--resume` 在哪个版本起可用，像 Codex 0.166 一样锁一个最低版本。

如果某个执行器不能按会话注入 MCP，退路是：这个执行器上的助手不拿编排工具，交付改为「Run 结束时服务从约定文件读交接记录」，并在能力检查里标出来。

### 1. P3-01 Claude 运行时适配器

- 在 `packages/runtime-claude` 里实现 `RuntimeAdapter`：CLI `-p --output-format stream-json --input-format stream-json`，`--permission-prompt-tool stdio` 走宿主审批，`--resume <session_id>` 恢复，中断用控制消息，必要时结束进程树。
- **用 CLI，不用 Agent SDK**（2026-11-25 已定）：CLI 已经在 P0 实测过，不给 PalDock 增加依赖，用户自己装 Claude Code 并登录，PalDock 只调用；Agent SDK 要先做许可证和分发审查，留到以后。
- 发现：PATH 上的 `claude`，或设置里填的路径；桌面版自带的那份路径随版本变化，只在设置里提示，不自动用。
- 环境变量用白名单（P0 的坑：继承 `CLAUDE_*` 会挂到宿主会话上）。
- 审批：`can_use_tool` 按工具名和参数映射到现有风险分级（`risk.ts`），与 Codex 的命令 / 文件改动分类并列。
- 用量：取 `result` 里的 `modelUsage`，主会话 + 子代理合计，记在 Run 上。
- 模拟执行器：给 Claude 也做一个离线 mock（同 Codex 的 mock 思路），CI 只跑 mock。

### 2. P3-02 角色与执行器设置

- 新表 `agent_profiles`（迁移 005）：角色、显示名、职责说明、提示词模板版本、首选执行器及备选、工作区权限（none / read / worktree-write）、交付范围（比如测试助手只交付测试目录、文档助手只交付 `docs`；P3-00 实测能强制的才当作限制，否则只是验收闸门核对的范围）、工具开关、预算（单次 Run 时长上限、并发）。出厂六个角色：协调、开发、测试、审阅、文档、调研。
- 执行器按角色选，可按项目覆盖，派单时可临时指定。硬约束只有能力检查：执行器报告的能力（工作目录限制、宿主审批、取消、恢复、MCP 注入）不满足角色需要时，界面提示并拒绝启动。只读角色（审阅、调研）只能用 P3-00 实测通过只读的执行器配置。
- 审阅与开发用同一执行器时只提醒，但审阅一定新开会话。
- 设置页：「设置 → 助手」，每个角色一行，显示当前执行器和能力检查结果。

### 3. P3-03 MCP 桥

- 每次 Run 启动一个 stdio 脚本（随应用分发），经本机 IPC 连回本地服务，作为 MCP 服务器注入这次会话。启动时注入一次性令牌和 Run ID，服务端只认令牌，不信模型自报身份；Run 结束令牌作废。
- 按角色暴露工具：
  - 协调助手：`propose_plan`、`get_status`、`send_followup`、`cancel`、`request_approval`、`post_summary`。
  - 专业助手：`get_task`（目标、验收标准、上游交接记录）、`submit_result`。
- 每个工具在服务端校验：调用者身份、任务归属、项目范围、角色能力、预算、并发、审批状态；返回结构化结果和可追踪 ID。工具调用写审计。
- 外部内容（渠道消息、网页、工具输出）不能借工具获得新权限：`propose_plan` 只产生待确认的计划，不直接执行。

### 4. P3-04 任务图调度器

- 计划确认后，子任务按依赖进入 `queued` / `waiting_dependency`；调度器只派依赖都 `succeeded` 的子任务；`succeeded` 指已经合入集成分支并通过集成检查，只通过自身检查不算（见下文「子任务状态与时序」）。依赖校验在 `propose_plan` 和确认计划时各做一次：角色存在、无环、目录在项目内、子任务数不超上限。
- 并发（沿用 ADR 0002，可配置）：全局 10 个模型调用、每任务 4 个并行子任务、同一助手会话串行。
- 上下文只传目标、验收标准、上游交接记录和必要文件路径，不传整段聊天。
- 失败：子任务 `failed` 时，下游进入 `blocked` 并写原因；协调助手被唤醒，可以提修改计划（重试、换执行器、拆分），修改计划同样要用户确认。自动重试只限无外部副作用的失败，每个子任务最多一次。
- 审批超时：沿用 30 分钟自动拒绝；拒绝后子任务按执行器结果走失败或继续。
- 取消：取消任务会取消所有未结束的 Run 和子任务，`waiting_dependency` 的直接 `cancelled`。
- 状态推进全部由事件驱动并校验 `version`，与 P1 的写入规则一致。

#### P3-04 实现要点（2026-11-25 开工前写定）

**存储（迁移 007）**

- `plans`：`id`、`task_id`、`revision`（第几版，`UNIQUE (task_id, revision)`）、`status`（`proposed` / `confirmed` / `rejected` / `superseded`）、`proposed_by_run_id`、`decision_note`、`version`（乐观锁，和其他状态表一样）、`created_at`、`decided_at`。「计划版本」用 `revision`，`version` 留给乐观锁，免得一个词两种意思。确认后不可修改，修改计划产生新的一行。
- `plan_nodes`：`plan_id`、`position`、`node_key`、`role`、`title`、`goal`、`paths`（JSON 数组）、`depends_on`（JSON 数组，存 `node_key`）。主键 `(plan_id, position)`，按计划读节点直接按主键顺序，不排序；`UNIQUE (plan_id, node_key)`。
- `subtasks` 加 `plan_id`、`node_key`：单子任务（P1 / P2 建的）两列为空，`getSubtaskOfTask` 只取 `plan_id IS NULL` 的那个；计划节点物化出的子任务带上它们。依赖沿用已有的 `subtask_deps`。
- 查询都给出 EXPLAIN QUERY PLAN 测试：按任务读计划（`plans_by_task`）、按计划读节点（主键）、按任务读子任务与依赖（`subtasks_by_task` + `subtask_deps` 主键）。

**domain 纯函数**

- `validatePlan(nodes, knownRoles)`：1–8 个节点；`node_key` 为小写字母开头的 `[a-z0-9-]`，计划内唯一；角色必须在设置里且不是协调助手；`depends_on` 只引用本计划内的其他节点；无环（Kahn 拓扑排序，报出环上的节点）；`paths` 是项目内相对路径：拒绝绝对路径（`/`、`\`、盘符）、`~`、任何 `..` 段。提议和确认时各校验一次（确认时角色设置可能已经变了）。
- `graphStep(nodes)`：给出一份任务图里该做的状态变化，按拓扑顺序一次算完（链式阻塞、链式解除都在同一步里）：
  - `waiting_dependency`：依赖都 `succeeded` → `queued`；有依赖 `failed` / `blocked` / `cancelled` → `blocked`，原因「上游「标题」失败 / 阻塞 / 已取消」。
  - 因上游被阻塞的 `blocked`（原因由 domain 生成、可识别）：上游恢复正常（重新排队、执行中等）后 → `waiting_dependency`，依赖都成功则直接 `queued`。因自身失败或服务重启而阻塞的不在此列，仍由用户选择恢复、重新开始或放弃。
- `taskStatusOf(current, subtaskStatuses)`：任务状态由子任务推导，单子任务和任务图共用一条规则（与 P1 的行为一致）：全部成功 → `succeeded`；全部结束且有取消 → `cancelled`，否则 → `failed`；有执行中 / 等审批 / 待验收 → `running`；有排队 / 等依赖 → 保持 `running`，否则 `queued`；剩下的都卡住 → `blocked`。状态机补两条转换：子任务 `blocked → waiting_dependency`（上游恢复），任务 `queued → blocked`（恢复程序本来就这么改，现在写进状态机）。

**流程**

- `propose_plan`（MCP，只有协调助手）：参数是任务标题、目标和节点列表；可带 `taskId` 给一个还在草稿的任务提新一版。没带时在协调助手这次 Run 所在的项目里建一个 `draft` 任务。新一版提出时旧的 `proposed` 版本置为 `superseded`。只产生待确认的计划，不派单。
- 桌面 IPC `plan.confirm` / `plan.reject`，都带计划的 `version`，先到者为准。确认在一个事务里：重新校验 → 计划 `confirmed` → 按节点建子任务和会话、写 `subtask_deps`（没有依赖的进 `queued`，有依赖的进 `waiting_dependency`）→ 任务 `draft → queued`；提交后把 `queued` 的交给监管器。退回写上原因，任务留在草稿，协调助手可以再提一版。
- 运行中改计划（确认后的新版本）留到 P3-08；P3-04 只允许给草稿任务提新一版。

**调度**

- 事件驱动：服务广播持久事件时，调度器收下 `subtask.status_changed`，只看属于计划的子任务，按任务去重后在下一个微任务里推进（不在别人的事务里写库）。推进 = 读这个任务的子任务和依赖 → `graphStep` → 逐个按版本迁移（先到者为准，冲突就跳过，等下一次事件）→ 重新推导任务状态 → 把新进入 `queued` 的交给监管器。
- 并发在监管器里统一管：全局 10（已有）、每任务 4（新增 `maxRunsPerTask`）；排队时跳过所在任务已满的，取下一个。同一会话串行：每个子任务一个会话，监管器按子任务只允许一次 Run；同一子任务重复入队会被忽略。
- 取消任务：计划草稿直接退回并取消任务；任务图里还没开始的（排队、等依赖、阻塞、待验收）同一事务直接 `cancelled`，运行中的交给监管器中断，收尾时记为取消。
- 每个计划节点有自己的 worktree 和分支（`paldock/<任务编号>-<节点键>`），从项目 HEAD 出发。下游暂时看不到上游的改动，要等 P3-06 的任务集成分支；在那之前，下游的提示词和 `get_task` 带上游的交接记录（`submit_result` 的摘要，没有时用最终回复）。
- 子任务做完仍进 `review`，P3-04 里由用户在任务详情里逐个「通过」放行下游；P3-05 的验收闸门接手后改为自动。

**不在 P3-04 做**：失败自动重试（最多 1 次）、唤醒协调助手（P3-07）、按角色的并发上限、计划卡片进「待我处理」（P3-08）、重启后重建就绪队列（P3-09）。

### 5. P3-05 交付、验收闸门与审阅助手

- 专业助手调用 `submit_result`，交接记录按 [Codex 与 Claude 协作开发规范](../../design/05-ai-collaboration.md)：变更、验证命令与结果、风险、下一步。子任务只能进 `review`。
- **验收闸门**：服务自己在该子任务的 worktree 里重跑计划中声明的检查命令，并核对 diff 只落在交付范围里。结果与声明不符就 `failed`，模型说「完成」不推进状态。检查结果和审阅意见都绑定被检查的提交 SHA，SHA 变了就要重跑。
- 检查命令仍需用户确认（P1 规则不变）：计划确认页里把每个子任务的检查命令一并列出，确认计划就是确认这些命令；之后新增的命令要再确认。
- **审阅是子任务内部的验收阶段，不是单独的子任务**：需要审阅的子任务，检查通过后由审阅助手（只读、独立会话）审该 SHA 的 diff。它不占「每任务最多 8 个子任务」的名额，不需要重新确认，也不会再触发审阅；审阅意见绑定到被审的那次 Run 和 SHA。
- **返工的终止条件**：审阅助手退回后自动重做，默认最多 2 轮；轮数用完或任务累计用时超过预算，子任务转 `blocked` 等你处理。你手动退回不限次数，只记录（ADR 0002 第 5 条）。
- 用户在「待我处理」里看到的验收对象，从单个任务变成「整个任务的汇总」加「标了需要人看的子任务」。

#### P3-05 实现要点（2026-11-25 开工前写定）

只管计划节点；P1 / P2 的单子任务仍由用户在桌面「继续 / 结束任务」，不变。

**存储（迁移 008）**

- `plan_nodes` 加 `check_command`（JSON，可空）：检查命令随计划一起提出、一起确认，确认计划就是确认这些命令；`propose_plan` 的节点多一个可选 `check`。
- `subtasks` 加 `gate_stage`（`review` 状态内的阶段：`review` 审阅中、`human` 交给人；空表示刚交付、还没过闸门）。子任务每次换状态都清空。
- `runs` 加 `purpose`（`work` / `review`）：审阅也是这个子任务的一次 Run，但用独立的会话（每轮审阅新建一个审阅助手会话，不沿用开发助手的会话和原生 thread），不改子任务状态；「最新一次 Run」只看 `work`。
- `run_results` 加 `commit_sha`、`out_of_scope`（JSON 数组）；`run_reviews` 加 `reviewer_run_id`、`commit_sha`：检查和审阅结论都绑定被检查的那个提交。一次审阅 Run 只能交一份结论（部分唯一索引）。
- 新事件 `gate.decided`（聚合 ID 为子任务）：阶段（检查 / 审阅）、结果（通过 / 退回 / 交给人）、原因。

**闸门（节点的工作 Run 成功结束后）**

1. 收集证据时把 worktree 的改动提交到节点分支，得到 SHA；改动文件列表（`base..SHA`）对照交付范围 = 角色的 `deliveryScope` ∪ 节点 `paths`（两者都空表示整个 worktree；不带通配符的路径按目录或文件前缀算）。Windows 上可写角色「不隔离」，越界就在这里抓。
2. 在这个 SHA 上跑节点的检查命令（有的话）。
3. 越出交付范围或检查没通过：子任务停在 `review`、`gate_stage = human`，原因写明越界的文件或检查结果，进「待我处理」，下游不放行。计划原写「不符即 `failed`」，改为交给人：`failed` 在 P3-08 之前是死路，而这里需要桌面上的人工覆盖。
4. 通过后：可写角色的节点交给审阅助手（`gate_stage = review`，执行器按审阅角色的设置，默认 Codex，只读）；只读角色的节点没有改动可审，直接通过。

**审阅**

- 审阅助手经 MCP `get_task` 拿到节点目标、上游交接、被审的 SHA、基线和改动统计，经新工具 `submit_review` 交结论：`accept`，或 `rework` 带理由。只有审阅 Run 能调用它，工作 Run 不能。
- 审阅 Run 结束后：通过 → 子任务 `succeeded`，放行下游（替代 P3-04 里手动点「通过」）；退回 → 回到开发助手同一个会话（沿用最近一次工作 Run 的 thread）按理由继续改，`rework_count + 1`；审阅 Run 失败、被中断或没交结论 → 交给人。
- 自动退回按已批准的计划 v2 最多 2 轮（`maxAutoReworks`，可配置），第 3 次退回转交给人；人在桌面退回不限次数。每次都记在 `run_reviews` 和事件里（ADR 0002 第 5 条「只记录」）。
- 人工覆盖：节点在 `review` 且没有 Run 在跑时，桌面可以直接「通过」或写理由「退回」，审阅中的要等这一轮结束。

**桌面**：节点行显示闸门阶段、最近一次检查（SHA、检查结果、越界文件）和审阅结论；计划待确认时列出每个节点的检查命令。

**不在 P3-05 做**：任务集成分支与合并（P3-06）、审阅超时、计划确认页里改检查命令（P3-08）、重启后继续未完成的审阅（P3-09）。

### 6. P3-06 任务集成分支与冲突

- 每个任务一条集成分支 `paldock/<任务键>`，从项目当前 HEAD 拉出；写入型子任务派发时，从集成分支的最新提交建自己的 worktree 和分支。
- **先出候选提交，检查通过再推进**：子任务检查和审阅都通过后，服务在一个临时 worktree 里从集成分支当前 HEAD 合并它的分支，得到候选合并提交，在候选提交上跑集成检查；通过后才用「旧 HEAD 必须不变」的条件把集成分支推进到候选提交。同一任务的合并串行。集成检查失败时集成分支不动，子任务 `blocked`，后续子任务仍从上一个通过的 HEAD 建 worktree。时序见下文。
- 全程本地操作，不推送、不碰用户自己的分支。**合进用户真正的分支仍是单独的、需要用户审批的操作**，P3 不做自动合并到 main。（2026-11-25 已定）
- 冲突：生成候选提交时冲突就中止，集成分支不动，子任务进入 `blocked`（原因「与 X 冲突」），协调助手被唤醒，可提一个「解决冲突」子任务；不自动选边。
- 并行写同一文件的子任务，在 `propose_plan` 时按交付范围做重叠检查并提示，不硬拦。

#### P3-06 实现要点（2026-11-25 开工前写定）

**存储（迁移 009）**

- `tasks` 加 `integration_branch`、`integration_worktree`、`integration_base`：计划确认时从项目当前 HEAD 建分支 `paldock/<任务编号>`，检出到数据根 `worktrees/<任务编号>-integration`（给人看、合并时快进它），记下起点。
- `merge_ops`：每次合并一行，`id`、`task_id`、`subtask_id`、`source_sha`（节点交付的提交）、`target_old`（合并前集成分支 HEAD）、`candidate_sha`、`phase`（`started` / `candidate` / `done` / `conflict` / `check_failed`）、`conflict_files`（JSON）、`detail`、时间。按子任务查最近一次走 `(subtask_id, created_at)` 索引；没结束的（`started` / `candidate`）配部分索引，留给 P3-09 的重启恢复。

**合并（节点通过闸门之后，替代 P3-05 的直接成功）**

1. 同一任务的合并串行（按任务排队）。写 `merge_ops`（`started`），记下集成分支当前 HEAD。
2. 在临时 worktree（数据根 `merges/<操作 ID>`，从旧 HEAD 分离检出）里 `merge --no-ff` 节点的提交，得到候选提交（`candidate`）。冲突就 `merge --abort`，记下冲突文件（`conflict`），集成分支不动。
3. 在候选提交上跑集成检查：已合入的节点和这个节点的检查命令（去重，按节点顺序）。失败记 `check_failed`，集成分支不动。
4. 通过后先确认集成分支还在旧 HEAD、任务没被取消，再在集成 worktree 里 `merge --ff-only` 到候选提交（分支和它的工作区一起前进，不用 update-ref 绕开工作区）；然后同一事务里 `done`、子任务 `succeeded`、记 `gate.decided`（合并阶段）、推导任务状态，调度器照常放行下游。
5. 冲突或集成检查失败：子任务停在 `review`、交给人，原因写明冲突文件或失败的命令，进「待我处理」。计划写的是 `blocked`，这里和 P3-05 一样改成交给人，因为桌面要提供两个选项：
   - **交回开发助手重做**：在节点 worktree 里把集成分支最新提交合进来（不提交，冲突文件留着冲突标记），节点的基线改为这个提交，回到开发助手同一个会话处理冲突；交付时的提交就是合并提交，范围按新基线核对，再走检查、审阅、合并。
   - **人工处理**：你在节点 worktree 里自己改好（路径在详情里），然后点「重试合并」（等同人工通过），重新走第 1 步。
- 人工「通过」（P3-05 的覆盖）同样走合并，不会跳过集成分支直接成功。没有集成分支的旧任务（P3-06 之前确认的）仍直接成功。

**下游基于集成分支**：节点的 worktree 从任务集成分支当时的最新提交建，上游合进去的改动下游都看得到；P3-04 留下的「下游看不到上游」到这里解决，提示词里那句说明随之去掉。

**全部通过之后**：任务成功，详情里显示集成分支和它的最新提交，标「待合并」。合进你真实分支由你自己用 git 做，P3 不做（计划 v2 已定，2026-11-25 再次确认）。

**worktree 准备命令**（2026-11-25 补）：新建的 worktree 没装依赖，`pnpm test` 这类检查会失败。项目设置里加一条可选的准备命令（结构化，不经 shell，默认不填，只在桌面设置，迁移 010）。计划节点的 worktree 第一次跑检查前执行一次（记 `prepared_at`，之后各次 Run 共用），合并候选 worktree 每次都是新的、有检查要跑时执行；失败和检查失败一样交给人，原因写「准备命令失败」，检查不跑。准备命令生成的文件（依赖目录）要在项目的 `.gitignore` 里，否则会被当成交付提交。

**不在 P3-06 做**：重启时按 `merge_ops` 补记或重试（P3-09）、唤醒协调助手提「解决冲突」子任务（P3-07）、提议计划时的交付范围重叠提示。

### 7. P3-07 协调助手主会话

- 桌面新增「对话」页：与协调助手的持续会话（PalDock 主会话），每个项目一个，可新开。
- **最小唤醒循环**：两种触发：用户消息、任务事件（子任务失败 / 阻塞 / 全部完成 / 审批被拒）。每次唤醒只处理一个事件，写 `wakes` 表并带去重键；同一主会话串行。单次唤醒软上限 20 次模型请求（提醒收尾）、硬上限 40 次（强制停止并告诉用户）。
- **上下文组装**（按顺序，超预算截断后面的）：模式说明与策略边界 → 当前会话滚动摘要 → 最近 N 条消息和本次事件 → 本项目任务板现状 → FTS5 检索到的历史片段。滚动摘要超长度阈值时生成，保留历史版本。
- 协调助手可以自己动手（在受控目录里），也可以 `propose_plan` 派单；简单问题直接回答。
- 汇总：任务全部结束后唤醒协调助手生成总结，经 outbox 回到发起的会话。
- 只有「项目协作」一种模式；其他模式在 P3.5。

#### P3-07 实现要点（2026-11-25 开工前写定）

**主会话怎么落库（迁移 011）**

- Run 必须挂在子任务上（`runs.subtask_id` 非空），所以每个主会话配一个「对话任务」：`tasks.kind = 'conversation'`（任务列表、/continue 都不列它），下面一个协调助手子任务（一直是 `draft`，不进状态机）和它的 `main` 会话。每个项目默认一个，「新会话」再建一个；消息照旧存 `messages`（FTS5）。
- `wakes`：会话、触发（`user_message` / `task_event`）、去重键（唯一：用户消息 ID、事件序号）、摘要、状态（`pending` / `running` / `done` / `failed` / `dropped`）、对应 Run、请求次数、时间。同一会话一次只跑一个。
- `user_notices`：协调助手经 `notify_user` 发给你的消息，自增编号即问题编号（`Q12`），类别（通知 / 问题）、状态（`open` / `read`）、升级时间。「待我处理」视图加 `notice`。

**协调助手的 Run**

- 监管器按任务类别区分：对话任务的 Run 不改子任务和任务状态、不建 worktree（工作目录是项目根目录，协调助手只读）、不收集证据；输出照旧合并成主会话里的消息。
- 每次唤醒一次 Run，沿用上一次的原生会话（thread），上下文连续；原生会话丢了才从头组装。

**唤醒循环**

- 触发：你在对话里发消息；属于这个会话提出的任务（计划的 `proposed_by_run_id` 所在会话）出现以下事件：节点阻塞、节点交给人（冲突、集成检查失败、审阅退回到上限、越界或检查失败）、任务全部通过、计划被退回、审批被拒或过期。每个事件一条唤醒，带一行事件摘要。
- 频率：任务事件触发的唤醒，同一会话两次之间至少 2 分钟（到点前的排队等），每天最多 20 次，超出的记 `dropped` 并给你发一条通知（ADR 0002「自动推进护栏」20 次 / 2 分钟）。你发的消息不受这个限制。
- 每次唤醒的请求上限 20 / 40（02「唤醒与触发器」）：CLI 执行器看不到每一次模型请求，这里按协调助手的 MCP 工具调用计数，作为近似。到 20 次时工具结果里提醒它收尾；第 41 次被拒绝，这次 Run 被中断，并通知你。
- 上下文组装（按顺序，超预算截断后面的）：模式说明与策略边界 → 本次事件或你的消息 →（新开原生会话时）最新滚动摘要和最近 10 条消息 → 本项目任务板现状 →（新开时）FTS5 检索到的这个会话的历史片段。
- **滚动摘要（最小版，2026-11-25 确认要做）**：每完成 20 次唤醒（`summaryEveryWakes`），或原生会话续不上要新开时，提示里要求协调助手结束前经 MCP `write_summary` 写一份；按会话带版本号存进 `session_summaries`，记下当时完成的唤醒数。原生会话续做失败时这次唤醒放回队列，下一次新开会话并注入最新摘要。原生会话的压缩只在单次 Run 内用，不作数据来源。长期记忆和摘要分层留到「模式与记忆」那一轮。

**notify_user**

- 协调助手的 MCP 工具：`notify_user`（正文、是不是问题）。先出现在桌面对话页和「待我处理」；你在桌面看过（打开对话页即标为已读）就不再外发。
- 没人看时按审批升级同一套规则（3 分钟无人处理、锁屏、空闲）发到所有已绑定的单聊，卡片带编号，提示回复时带上编号。外部回复交回提问的助手在 P3-10 做；在那之前外部回复仍按 P2 的规则处理。

**桌面**：新增「对话」页：选项目、选会话或新建，消息列表、输入框、协调助手的通知（带编号）和最近几次唤醒的状态。

**不在 P3-07 做**：长期记忆与摘要分层、定时触发器、任务结束后经 outbox 汇总回外部发起处（P3-10 外部消息进主会话时一起做）。

### 8. P3-08 计划确认、任务图界面、自动处理记录单

- 计划卡片：子任务列表（角色、执行器、目标、验收标准、依赖、交付范围、检查命令），可以改执行器、删子任务后再确认，也可以退回让协调助手改。
- **确认时重新校验并锁定版本**：确认在一个事务里对整份计划重新校验（依赖无悬空、无环，执行器满足角色能力，子任务数和预算不超），通过后生成一个不可变的计划版本；调度器只执行已确认的版本。
- **运行中改计划**：新版本确认后，已完成且没改的节点保留结论；被删的节点取消它的 Run；改了目标、验收标准、检查命令或依赖的节点按新节点重新执行，不沿用旧的成功结论；没开始的节点按新版本替换。被作废的 Run 失去提交资格（见下文）。
- 任务详情：任务图（列表 + 依赖缩进即可，不做画布），每个子任务按时间列出各次 Run（角色、实际执行器、会话、产物、检查结果、用量）。
- **自动处理记录单**：新表 `auto_decisions`，凡是没经过用户的决定都留一条（跳过计划确认、跳过审阅、按等级自动批准）。P3 默认**不跳过计划确认**，开关在设置里，默认关；记录单页面先只读，补审和撤销在以后。

#### P3-08 实现要点（2026-11-25 开工前写定）

**存储（迁移 012）**：`plan_nodes` 加 `executor`（确认前可改，空表示按角色设置）；`workspaces` 加 `auto_policy`（JSON，默认全关）；新表 `auto_decisions`（项目、任务、计划或子任务、类别、原因、时间，按项目和时间查）；计划状态机补 `confirmed → superseded`（运行中确认了新一版）。

**确认前修改**（计划还在 `proposed`，带计划的 `version`，先到者为准）：改某个节点的执行器、改或去掉检查命令、删节点（有别的节点依赖它时拒绝）。每次修改都重新跑 `validatePlan`，通过才写入。确认后不可修改。确认和退回都可以带意见；退回本来就唤醒协调助手，确认带了意见时也唤醒它，把意见交给它。

**执行器**：计划节点有自己的执行器时用它，否则按角色在项目里的设置；能力检查照旧在启动 Run 前做。详情里显示每个节点实际会用的执行器。

**运行中改计划**：任务确认后，协调助手仍可给它提新一版（任务没结束就行），你确认后：
- 按节点键对照新旧两版：角色、目标、路径、依赖、检查命令、执行器都没变的节点沿用原来的子任务和结论（换挂到新版本上）；
- 改了的节点按新节点重新执行（原子任务没结束就取消，有 Run 在跑就中断），新子任务从集成分支最新提交出发；
- 新版本里没有的节点：没结束的取消；
- 旧版本的子任务从此不算进任务状态和任务图；被取消的子任务的 Run 迟到交付时，交接记录照样存档，但子任务已不在待验收，闸门、合并和放行下游都不会发生（失去提交资格）。

**自动处理**（按项目设置，默认全关，只在桌面改）：

### 9. P3-09 多子任务的重启恢复

- 服务重启后：进行中的 Run 走现有恢复逻辑（`interrupted` / `unconfirmed`，按原生 ID 查实后更新）；调度器按持久状态重建就绪队列，不重复派已经开始过的子任务；`wakes` 去重键保证主会话不对同一事件回复两次。
- **合并按操作记录恢复**：每次合并先写合并操作记录（`merge_ops`：操作 ID、子任务、源 SHA、目标旧 HEAD、候选 SHA、阶段），重启时对照 Git 和数据库决定补记、重试或交给人处理，覆盖「Git 已推进、数据库未落」的窗口。细则见下文时序第 5 步。
- 取消和合并共用同一把任务锁：取消要等锁；合并在推进分支前再确认任务没被取消。
- 外部副作用（出站消息）沿用 outbox 的 `unknown` 不重发规则。

#### P3-09 实现要点（2026-11-25 开工前写定）

启动顺序不变：存储层的 `interruptActiveWork` 先把没结束的 Run 记 `interrupted`、排队和执行中的子任务记 `blocked`（P1 / P2 的单子任务仍由你在「待我处理」里选恢复、重新开始或放弃，不变）。然后新的恢复程序（`RecoveryService`）只收拾 P3 的中间状态，每一项都写一条 `recovery.performed` 事件（类别、对象、结果、说明），本次启动恢复了什么在桌面「待我处理」顶部列出。

- **计划节点的工作 Run**：有原生 thread 和 turn 的，先按 `checkTurn` 查实（Codex `thread/read`，Claude 核对 transcript 里的这一轮）：
  - 已完成：补记结果：Run 记成功（状态机补 `interrupted → succeeded`，只在查实后用），照常收集证据、提交、进闸门；
  - 已失败：Run 记失败，节点保持阻塞，原因写执行器的错误，下游由调度器阻塞；
  - 进行中、查不到或被中断：按原 thread 续做（新 Run 指回原 Run）；没有 thread 的重新开始。
  - 因重启被阻塞、但从没开始过的节点（排队中被打断）：直接重新排队。
- **审阅中的节点**（`review` + 审阅中，审阅 Run 已被中断）：用新的独立会话重新发起审阅。
- **合并**（`merge_ops` 停在 `started` / `candidate`）：对照集成分支现在的 HEAD：
  - 等于候选提交：Git 已快进、数据库没记完：补记 `done`，节点成功；
  - 等于合并前的 HEAD：还没推进：这次操作作废（记 `check_failed`，说明「服务重启，重做合并」），从头再合一次；
  - 都不是：分支被别人动过，交给你。
  - 清掉残留的临时合并 worktree（`merges/<操作 ID>`），集成 worktree 里有 `MERGE_HEAD` 等残留时 `merge --abort`。节点 worktree 里「交回重做」故意留下的合并状态不动。
- **唤醒**：正在跑的唤醒放回队列（原来是记失败），沿用原生会话；频率计数照旧按库里的开始时间算，不会因为重启多出次数。
- **notify_user**：没外发的通知本来就在库里，渠道的升级扫描照常继续，不用特别处理（事件里记一条有几条待外发）。
- **调度器**：恢复完对每个没结束的计划任务重新推进一次（`graphStep`），把就绪的节点交给监管器；已经开始过的不会重复派（监管器按子任务去重，状态都按版本迁移）。

测试（`tests/integration/p3-restart-recovery.test.ts`）用落盘的数据库，在关键点「杀掉」服务（停掉组件、关库，不跑正常退出的收尾），再按启动顺序重开：工作 Run 中（三种 `checkTurn` 结果）、排队中、审阅中、合并的每一步（出了候选未快进、已快进未记完、只写了 started）、唤醒中。
合并的关键点用 `IntegrationService` 的测试钩子停住（只在测试里注入）。

### 12. 原生会话复用（2026-11-26 你定，0.3.3）

0.3.1 实测：Codex 应用里每个子任务、每轮审阅都多一个会话，协调助手的会话里每一轮都重发整段角色说明和任务板，既乱又费 token。改为：

### 13. 项目级助手设置（2026-11-26 你定，0.3.4）

4. **每个角色的隔离方式**

- 新项目默认共用当前工作区；已有项目保持现状，在项目页一键切换。
- 同一个项目里所有 Run 一律排队（同一时刻只有一个助手在这个工作区里）。
- 合并先只做本地合并加推送，远端 PR 以后再说。
- 推送、合并按高风险处理。
- 强推、硬重置、删除远端分支只能在桌面单独授权。

**1. 共用工作区（「当前工作区」模式）**

- 项目页的工作区方式加一个项目级开关：「当前工作区」（新项目默认）/「独立 worktree」（现在的做法）。当前工作区下，所有角色都在项目根目录里工作：不建 worktree、不建集成分支、不合并；开发改完，测试和审阅看到的就是同一份未提交的改动。
- 同一项目的 Run 一律排队：不只写入者，测试会生成快照、改受版本控制的文件，审阅读的时候也不能有人在写。代价是同一项目里不并行；不同项目照旧并行。
- 计划节点通过闸门（检查、审阅）即成功，不再有「待合并」；任务结束时显示「改动在你的工作区里，还没提交」，并列出这个任务改了哪些文件。
- 角色会话复用照旧（工作目录每轮都是项目根目录）。

**2. 精确知道「这次改了什么」，不碰你的东西**

- 每次 Run 开始和结束时给整个工作区各拍一个快照：用临时索引（`GIT_INDEX_FILE` 指向数据根下的临时文件）把工作区所有文件（含未跟踪、尊重 `.gitignore`）写成一个 git tree，只写对象库，不动你的暂存区、工作区和分支。
- 两个快照的差就是这次 Run 的改动，精确到改动块；任务的改动是它各次 Run 改动的合集。这同时取代 0.3.5 的内容指纹，交付范围核对按这个差来算。
- **实现边界**（Codex 补充，已采纳）：快照只能识别「变了什么」，不能证明「是谁改的」。Run 期间你和助手都改过的内容会一起出现在快照差里。所以「只提交这次修改」一律展示拟提交的改动块，PalDock 不会替你判断归属后整文件提交。
- **默认勾选要有写入证据**（Codex 补充，已采纳）：即使同一时刻只有一个 Run，你也可能在 IDE 里改别的文件，只凭时间和快照差不能算助手的。PalDock 记录助手的写入：Codex 的 fileChange 条目（路径和补丁）、Claude 的 Edit / Write / MultiEdit 请求（路径、替换前后的文本或写入内容）。只有能用这些记录核对出具体内容、并且当前文件内容仍与记录吻合的改动块才默认勾选；其余（包括助手经命令写的文件，例如测试生成的快照）标为「本轮期间发生的改动」，默认不勾。

**3. 编辑、提交、推送、合并分开指挥**

- 「修这个问题」：只编辑和测试，任何角色都不能 commit / push / merge（`git commit`、`git push`、`git merge`、`git rebase`、`git reset` 在命令分类里已经是要审批的高风险，当前工作区模式下由宿主直接拒绝，提示用对话里的提交命令）。
- 协调助手（单人模式下是单人助手）多三个 MCP 工具，都只产生「待你确认」的卡片，确认后由宿主执行，助手自己不碰 git：
  - `propose_commit(message, scope)`：scope 为「这个任务的改动」或「这次对话以来的改动」。卡片展示仓库、当前分支、HEAD、拟提交的改动块（按上面的写入证据决定默认是否勾选）、你已暂存的内容（保持不动）。确认后：在临时索引里把选中的改动块应用到 HEAD 上，生成提交并推进当前分支；你的工作区文件不动。提交前再核对一次当前分支和 HEAD，变了就作废这张卡片。
  - **保留你的暂存差异**（Codex 补充，已采纳）：推进分支后，每个涉及的文件重新算索引项——以新提交里的内容为底，把你原来的暂存差异（原索引相对原 HEAD 的补丁）重新打上去。例：你暂存了第 10 行、助手改了第 80 行、只提交第 80 行，结果是新提交只含第 80 行，`git diff --cached` 仍只有你的第 10 行，工作区保留双方的修改。你的暂存块和要提交的块重叠、补丁打不上时，在推进分支之前停下，列出这个文件让你选（先提交你的、只提交助手的、或取消），不会留下「撤销第 80 行」这种多出来的暂存改动。
  - `propose_push(remote?, branch?)`：缺省推当前分支到它的上游。卡片展示远端名和地址、远端分支、要推的提交列表；确认前核对当前分支、上游和受保护分支规则（远端拒绝时如实报错）。用本机已有的 git 凭据，不经 PalDock 存凭据。
  - `propose_merge(source, target)`：本地合并。卡片展示源分支、目标分支、要合入的提交、是否快进；确认后在当前工作区之外的临时 worktree 里合并并推进目标分支（目标是当前分支时，要求工作区干净或只有你确认过的改动，否则拒绝并说明）。冲突时不落地、列出冲突文件交给你。远端 PR 合并以后再做。
- 这三类卡片走现有的审批：推送、合并按高风险，外部渠道只有 L2 能批；提交按中风险。强推、硬重置、删除远端分支不提供工具，助手用命令做时一律拒绝，只能你在桌面「单独授权」一次（卡片上写明后果）。
- 每次提交、推送、合并都写审计和「自动处理记录」之外的操作记录（谁指示的、哪个渠道、目标分支、提交 SHA）。

**4. 绑定明确目标（分支保护）**

- Run 开始时记下仓库根目录、当前分支、HEAD。**核对点**：每轮开始前、审批放行前、Run 结束取证时、提交和推送前（合并前核对源和目标）。任一处不符就不放行。
- **运行中监视**：Run 进行期间用 fs watch 监视 `.git/HEAD`（项目本身是 worktree 时监视它 gitdir 里的 HEAD），再加每几秒一次的兜底轮询（watch 在 Windows 上可能漏事件）。检测到切换后：中断这一轮 turn，终止这个 Run 的整棵命令进程树（含正在跑的测试和检查命令），暂停这个项目后续的写入型 Run，「待我处理」和对话里提示「分支从 A 变成 B，已暂停」，等你在桌面上选「在新分支上继续」或「取消」。
- **做不到的**：检测到之前已经启动的进程，可能已经在切换后的工作区里写了文件，PalDock 无法撤销。只能用 Run 开始时的快照和当前工作区比对，列出这段时间变动的文件，在提示里报告给你。
- 分离 HEAD（detached）时不开始写入型 Run，提示先切到分支。

**4b. 顺带修的 worktree 模式老问题**（Codex 复审，2026-11-26 核实属实，并进 0.3.6）

- **集成检查的证据要落库**：节点没有改动时候选提交可能就等于原集成分支（`integration.ts:62` 的恢复判定、`:192` 起的候选与检查顺序），在候选已记录、检查还没跑完时被杀，重启后会只凭「分支停在候选提交」补记成功。改为检查通过后先在 `merge_ops` 记下检查通过的时间，再快进；恢复时只有「分支在候选提交且（候选不等于原分支，或有检查通过记录）」才补记，否则重跑检查。验收：集成检查明确失败的节点，在候选已记录时被杀，重启后不放行下游。
- **自动合并只合审过的提交**：合并源现在取节点分支当前的提交（`:175`），审阅通过 A 之后节点分支又多了 B，B 会被一起合进去。改为自动合并（检查 / 审阅通过后）用交付证据里绑定的那个提交；节点分支在那之后又有新提交时不合并，交给你。你在桌面上「我已处理，重试合并」时才用节点分支当前的提交。验收：审阅通过 A、排队期间节点分支新增 B，B 不会被自动合入。
- **恢复时先清理再重试**：重启恢复在循环里就启动了合并重试（`:74`），随后的清理（`:88`）会删掉 `merges/` 下所有目录，可能把刚建好的重试目录也删了。改为先收集要重试的项、清理上次留下的临时 worktree，最后再启动重试。验收：两个任务同时恢复，新建的重试目录不会被这一轮清理删掉。

**5. 数据**

- 迁移 017：`workspaces` 加 `workspace_mode`（`current` / `worktree`，新项目 `current`，已有项目迁移为 `worktree`）；`run_snapshots`（Run ID、开始 / 结束 tree、分支、HEAD）；`git_ops`（类型 commit / push / merge、状态、目标、提交 SHA、审批 ID、来源渠道、时间）。
- 角色的隔离方式在「当前工作区」模式下只剩「可写」和「只读」两档（只读照旧用只读沙箱）。

**6. 测试**

- 离线：助手改 A、你同时改 B，B 不会被默认勾选；你暂存第 10 行、助手改第 80 行、只提交第 80 行后，提交只含第 80 行、`git diff --cached` 只有第 10 行、工作区两边的改动都在；两块重叠时停下不推进分支；当前工作区下开发 → 测试 → 审阅都在项目根目录、测试看得到未提交改动；同一项目 Run 排队；快照差只含助手改动、你的暂存 / 未暂存 / 未跟踪内容前后一致；提交只含选中的改动块、你的暂存内容保持、分支变了卡片作废；推送 / 合并的目标核对与拒绝；切分支后暂停；强推等被拒；已有项目迁移后仍是 worktree 模式。
- 实机（你的端到端场景）：在一个已有你暂存内容的功能分支上，Codex 改代码、Claude 测试并审阅；改动立即出现在原 IDE 目录，Claude 验证到尚未提交的新行为，你原有的暂存内容完整；然后「只提交这次修改」，验收同时检查两点：新提交只包含勾选的改动块；你原本暂存的内容在提交后仍是暂存状态；再「推送当前分支」核对远端目标（用一个临时远端仓库，不推你的真实远端）。
- 实机补充：「测试正在运行时切分支」。记录实际行为：从切换到检测到的延迟、切换后哪些进程实际停止了、终止前已经写入了哪些文件、报告里列出的变动文件是否和实际一致，以实测结果写明保护边界。

**7. 不做**

远端 PR 合并、自动推送、多工作区同时写同一仓库、跨项目共享工作区。

### 15. 只提交这次、只推送看过的、审批分层（2026-11-26 你定，0.3.7）

Codex 复审 0.3.6 的四项（都核实属实）加审批分层。验收口径按你 08:03 的要求。

**1. 只提交这次：严格限定任务或对话，按块不按文件名**

- `propose_commit(message, taskId?, wholeProject?)`：默认范围是这个对话发起的任务（加上协调助手自己，单人模式时它也改文件）；填 `taskId` 时只看这个任务，必须是这个对话发起的；`wholeProject` 只在你明确要求时用。卡片写明范围。
- 归属逐行算：把这段时间的快照串成一条合成提交链 HEAD → 开始₁ → 助手重放₁ → 结束₁ → 开始₂ → … → 现在，用 `git blame`（加的行）和 `git blame --reverse`（删的行）找出每一行是在哪一步变的。只列有范围内 Run 期间改动的块；别的任务的块、你在 Run 之外改的块不列。
- 不再按「上次提交」的时间截断：已经提交的块在 HEAD 里，自然不在差异里；提交了任务 B 之后，任务 A 还没提交的块照样在。

**2. 默认勾选：补丁一致，而且有对应到这一块的写入证据**

- 「助手重放」是从这次 Run 开始时的内容出发、只重放助手自己报告的写入得到的版本：替换的原文必须唯一，补丁严格打（不模糊匹配），整文件写入记下写之前文件内容的摘要，期间有人改过就不算证据。对不上的文件这次 Run 没有证据，块列出但不勾。
- 一个块默认勾选，要求它的每一行都是范围内助手自己的改动（落在「助手重放」那一步）。你在 Run 期间改的落在「结束」那一步，列出不勾；Run 之后改的不属于这次，不列；挨着别的改动、被 `-U1` 并成一块的不勾。宁可少勾。
- Codex 的 fileChange 按类型记：新建是全文（以 `@@` 开头时是补丁），修改是统一补丁，删除和改名不记。

**3. 推送、合并按预览的 SHA 执行**

- 推送卡片锁定预览时的 HEAD，确认后推的是它（`<sha>:refs/heads/<分支>`），不是确认那一刻的分支。
- 目标状态取实际推送地址：`git remote get-url --push --all` 的每个地址都用 `ls-remote` 现查，不用本地的 `origin/分支`。几个地址状态不一致、远端有本地没有的提交、不是快进，都直接说明，不提出卡片。卡片列出全部会写入的地址和提交总数。
- 确认时再查一次，HEAD、地址、任一地址上分支的状态变了就作废。推送带租约（`--force-with-lease=<ref>:<预览时的提交>`，新建分支是空值，表示必须还不存在），只用来核对远端没被别人动过；预览时已确认是快进，所以不会强推。
- 合并卡片锁定源和目标两边的提交，任一边变了就作废，合并的是那个源提交。

**4. 暂存区是你的**

- 拒绝规则补上 `git add` / `rm` / `mv` / `update-index` / `read-tree` / `worktree`（`restore --staged`、`reset`、`stash` 原来就有）。
- Codex 沙箱里的命令宿主拦不住，所以每轮开始和结束时各记一次暂存区（复制索引后 `git write-tree`，不动你的索引文件）。变了就暂停这个项目，在对话里提出「保留 / 恢复」卡片，默认不自动恢复。
- 点「恢复」时先核对现在的暂存区还等于弹卡时的，不等就作废，不覆盖你刚做的；恢复用 `git read-tree` 回到这一轮开始前的 tree，只改索引，工作区文件不动。
- 读不出暂存区（`git write-tree` 失败，比如有未解决的合并冲突）：开始时不开始这一轮，结束时暂停项目，都照实写明原因，不当成「没变」。
- 宿主自己改暂存区（提交卡片、恢复卡片）后，正在跑的 Run 以新的暂存区为准，免得误报。

**5. 项目外只读访问的审批分层**

- 原来为什么是「高风险、只能拒绝」：Claude 读允许范围之外的文件要审批，PalDock 的映射只认 shell 和写文件两类工具，其余（Read / Glob / Grep 也在内）一律归为「权限扩展」；权限扩展按高风险，P1 定的是任何一端都不能批准，所以桌面按钮是灰的。Codex 那边批准了也只回空权限。
- 现在：只读工具（Read / Glob / Grep / LS / NotebookRead，不含 shell）单独识别，按路径分层：
  - 都在项目里，或都是这一轮生成的文件（真实路径的创建时间不早于 Run 开始）：直接放行，记 `approval.auto`；
  - 有敏感路径（家目录下的 `.ssh`、`.aws`、`.codex`、`.claude`、浏览器配置、系统凭据目录，任何位置的 `.env*`、`*.pem`、`*.key`、私钥，PalDock 数据目录）：高风险，只能你批，「允许一次」可用，协调助手不能批；
  - 其余项目外只读：交协调助手判断（MCP 工具 `decide_approval`：allow / deny / unsure），记 `approval.coordinator`；发起读取的 Run 不能自批；它拿不准、超时（90 秒）或项目没有主会话时回到你这里。
- 其他原来只能拒绝的权限扩展（联网、项目外写入等）：你可以「允许一次」；Codex 只在你批准时授予它请求的权限，只限本 turn。外部渠道仍只能拒绝这类（含敏感路径的读取），批准请到电脑上。
- 同一次 Run 3 秒内的审批合成一组：「待我处理」一张卡（「全部允许一次」「全部拒绝」和逐项处理），外部渠道一条消息；各项仍独立审计、独立过期。交给协调助手判断中的不外发。

**6. 数据**：迁移 018——写入记录加写之前的摘要；卡片加「暂存区」一类，升级前没处理的卡片作废；审批加只读、敏感、组、交给协调助手几列。

**7. 测试**：见 checklist 1d。实机：同项目两个任务改同一文件的不同块（A 用 Codex、B 用 Claude），在 B 的对话里只提交 B 再推到临时远端，之后在 A 的对话里提交 A。

### 16. 协调助手在发起的对话里找你批（2026-11-26 你提出并同意，0.3.8）

**目标**：需要你决定的事，默认由协调助手在发起任务的那个对话里找你：桌面发起的在桌面对话页，飞书 / Telegram 发起的回到原会话。它用一两句话说清哪个助手在做什么、为什么需要你决定、建议怎么处理；你可以追问、只批其中一项、看到任务继续。「待我处理」保留作记录，日常不必打开。确认仍由 PalDock 执行并留痕。

**发布条件**（你定的）：审批期间能正常对话；新事项不能改变一句「可以」的对象。

**1. 审批对话不排工作区的队**

- 团队模式的协调助手本来就不占项目的执行名额（0.3.6 起只有在项目目录里干活的 Run 排队，协调助手只读），所以测试助手占着名额等你批准时，协调助手照样能被唤醒、通知你、回答追问。这条作为第一个端到端测试来验证：原任务挂着时，通知和追问都能完成。
- 审批对话这一轮协调助手只能解释、登记建议、转交决定：宿主给它的唤醒里写明这一点；它这一轮里要是又提计划、提交、推送，照常走各自的卡片，不影响等待中的审批。
- 单人模式下发起请求的就是主会话自己，它在等审批、没法开口：宿主直接在这个对话里发一条说明（哪个工具、什么目标、为什么要你决定），带按钮；你的文字回复要等它这一轮结束后才处理，所以单人模式以按钮为准。
- 协调助手正在忙别的（上一轮还没结束）或不可用时：宿主等它最多 20 秒；它还没发出问题，就由宿主在这个对话里发一条说明（同上），不让请求静默挂着。

**2. 一句「可以」只对应你看到的那个问题**

- 每个对话同一时刻只有一个「正在问你的问题」（下文叫问题，宿主里的记录是建议）。问题没解决时，新来的事项不打断它，排在后面；这个问题解决或过期后，协调助手再问下一个。所以你打字期间来了推送请求，你发出的「可以」仍然只对应原来那个读图的问题。
- 协调助手只有在你回复之后才能改写问题（比如你说「只要第一张」时，它可以把问题改成「只放行第一张？」）。改写会作废旧问题的按钮；外部渠道里你引用旧消息回复时，只对应旧问题（旧问题已作废就告诉你，不执行）。
- `userMessageId` 只能证明你说过话，不能证明你同意了。宿主还要求协调助手给出你那句话里表示决定的原文（`decisionQuote`），并核对：
  - 它确实出现在那条消息里；
  - 那条消息不是单纯的提问（以问号结尾、又没有「可以 / 行 / 好 / 同意 / 允许 / 放行 / 批 / 不用 / 不要 / 拒绝」之类表示决定的词）。
  所以「为什么要读第二张？」不会触发放行；协调助手先回答，问题继续挂着。
- **低风险的文字审批看完整句意**：判断你是不是同意，靠协调助手读懂整句话；引用原文是为了留痕，不是靠关键词放行。「我还没说可以」「为什么要我点允许？」都带着肯定词，但都是待决：协调助手不能转交决定，意思不清楚时在原对话追问一句。宿主再兜一层底：那句话带否定（还没 / 没说 / 不是 / 先别 / 等等 / 别 …），或者是提问（问号结尾，或者以为什么 / 怎么 / 是不是 开头），一律拒绝转交，让协调助手去追问。这两句都写进测试。
- 普通追问不弹新卡片，问题原样挂着。

**3. 谁发起、谁建议、谁授权**

- 限制的是决定者，不是发起者：协调助手不能用 `decide_approval` 批它自己的 Run 发起的请求；你可以批准任何请求，包括协调助手用 `propose_push` 等提出的 Git 卡片。
- 推送、合并、敏感路径的读取、项目外写入这类高影响操作：问题里必须写明目标（远端地址和分支、源和目标、具体路径），宿主在唤醒内容里给出这些信息；放行要点原消息下面带目标的确认按钮（例如「推送 a1b2c3d 到 origin/main」），文字回复只用来追问和拒绝。
- 提交卡片绑定具体改动块：问题里列出要提交的块，你说「只提交第二块」，协调助手交上来的就是那一块的编号，宿主只提交它，不会退回到默认勾选项；没有给出块编号的提交决定一律拒绝。

**4. 部分批准、剩余事项、防重复执行**

- 宿主把问题绑定到：来源会话、可以授权的用户（这个对话的你；外部会话是绑定的那个账号）、各项的编号和版本。
- 「第一张可以」只放行第一张，第二张继续等待（问题改成只剩第二张）；「第一张可以，第二张不用」才两张都处理；「都不要」只拒绝这个问题里列出的项。
- **部分批准后，旧按钮不能处理剩余项**：「第一张可以」之后，第一张只执行一次，原来整组的按钮（「按建议处理」「都不要」）全部失效；第二张如果还要你决定，由协调助手重新问，问题里只有第二张，按钮也只对应第二张。这时即使来了推送请求，它也排在后面：你可以继续追问第二张，推送始终要你单独点它自己的确认按钮。
- 文字回复、按钮、外部渠道的重投共用同一次决定：每项带版本号执行，先到者为准，后到的告诉你「已经处理过」。测一次：先回「可以」，再点旧按钮，确认审批或 Git 操作只执行一次。

**5. 「只通知一次」要区分已发出和已送达**

- 协调助手的问题发到外部会话时，以投递成功为准。投递失败、协调助手离线、或者这个渠道只能拒绝这一项时，在桌面「待我处理」里保留可以直接处理的入口，并照现有规则提醒；不会让请求静默过期。
- 已经成功送达的问题不再重复提醒（「待我处理」里只是记录）。
- 敏感路径：外部会话里只说「有一项需要到电脑上确认」，不写完整路径；完整路径只在桌面显示。
- 来源缺失（比如单独建的任务，或者提出计划的主会话已经不在了）：回到这个项目的桌面入口（「待我处理」和项目页），不借用某个恰好绑定了外部聊天的主会话。

**6. 工具**

- `suggest_decision(text, items: [{ ref, decision, hunkIds? }])`：协调助手登记它的问题（明确建议）。`ref` 是审批编号或 Git 卡片编号；`decision` 是 allow / deny（Git 卡片是 confirm / cancel）；提交卡片要带 `hunkIds`。一个问题只涉及一件事（同一类审批，或一张 Git 卡片）。对话里已经有问题时只能在回应你的回合里改写它，否则拒绝并让它排队。
- `resolve_approvals(suggestionId, items: [{ ref, decision, hunkIds? }], userMessageId, decisionQuote)`：把你的决定交给宿主。宿主只在下面这些都满足时执行：
  - 这一轮是你在这个会话里的新消息触发的，`userMessageId` 就是那条消息，在问题之后；
  - `decisionQuote` 核对通过（见第 2 条）；
  - `items` 都在这个问题里，每项可以批或不批，不能多出问题之外的项；
  - 每项还在等待、版本对得上、属于这个项目；
  - 渠道有权限：外部渠道按远程审批等级（L0 / L1 / L2）；高影响操作的放行只认按钮（见第 3 条）。
  不满足的拒绝，并说明原因（「这条消息早于问题」「推送请点消息下面的确认按钮」「推送目标变了」等），由协调助手转告你，告诉你下一步。
- 按钮：问题下面的按钮等同于同意那个问题（或其中带目标的那一项），宿主直接执行，不经协调助手。
- 执行之后，宿主把结果（哪几项已放行、哪个节点继续了、哪些还在等）交回协调助手，由它在原对话里告诉你，例如「第一张已放行，测试继续了；第二张还在等你」。

**7. 留痕**

- 每项单独记审计 `approval.conversation`：协调助手 Run、问题编号和原文、你那条消息的编号、`decisionQuote`、渠道、每项的决定。点按钮的记 `approval.suggestion`。
- 审批的「决定来自」记成你发消息的渠道。

**8. 数据**：迁移 019——`approval_suggestions`（会话、协调助手消息、Run、问题原文、各项（编号、版本、决定、提交块）、状态：等待 / 已改写 / 已执行 / 失效、送达状态、时间）；问题之外排队的事项不另存（就是还没进问题的待审批和卡片）。

**9. 测试**

- 离线：
  - 原任务挂着等审批时，协调助手能被唤醒、发出问题、回答追问（第一个端到端测试）；
  - 你打字期间来了推送请求：「可以」只对应读图的问题，推送没执行；
  - 「为什么要读第二张？」不触发放行；没有新消息、消息早于问题时拒绝；
  - 部分批准：「第一张可以」只放行第一张，第二张仍在等；「都不要」只拒绝列出的项；
  - 先回「可以」再点旧按钮，只执行一次；
  - 你可以批准协调助手提出的推送卡片，协调助手不能批自己的请求；提交只提交你说的块；推送、合并要按钮；
  - 投递失败、协调助手不可用时桌面有可处理的入口；敏感路径在外部会话里不写路径；来源缺失回到桌面；
  - 飞书 / Telegram 发起的任务，问题发回原会话；过期、目标变了、渠道权限不够时说明原因和下一步。
- 离线还要覆盖：「我还没说可以」「为什么要我点允许？」保持待决；部分批准后旧的整组按钮点了无效，第二张的新问题只对应第二张；部分批准之后来了推送请求，追问第二张不受影响，推送没执行。
- 发布验收（真实场景）：任务挂起等审批时，你在原对话里收到解释、追问一次、部分放行，并看到哪一步已经继续，全程不用打开「待我处理」。真实 Claude 测试助手读项目外两张图，你在桌面对话里追问一次，然后部分批准。再加一幕：你正在回答读图时来了一个推送请求，你说「第一张可以」，最终只读了第一张，第二张仍在等，代码没有推送。

## 子任务状态与时序

### 子任务状态

`subtasks.status` 沿用现有取值，`review` 内再用 `gate_stage` 分为检查（check）、审阅（review）、合并（merge）三段，不改表的 CHECK 约束。

| 从 | 事件 | 到 | 说明 |
|---|---|---|---|
| `draft` | 计划版本确认 | `queued` / `waiting_dependency` | 依赖没有全部 `succeeded` 的进 `waiting_dependency` |
| `waiting_dependency` | 依赖全部 `succeeded` | `queued` | |
| `queued` / `waiting_dependency` | 某个依赖 `failed` / `cancelled` / `blocked` | `blocked` | 写明原因 |
| `queued` | 调度器派发 | `running` | 从集成分支当前 HEAD 建 worktree，新 Run |
| `running` | 执行器请求审批 | `waiting_approval` | |
| `waiting_approval` | 批准 / 拒绝 / 超时 | `running` | 拒绝或超时后由执行器决定继续还是失败 |
| `running` | Run 失败且不能自动重试 | `failed` | 下游 `blocked` |
| `running` | 有提交资格的 `submit_result` | `review`（check） | 记下提交 SHA |
| `review`（check） | 检查通过 | `review`（review）或 `review`（merge） | 不需要审阅的直接进合并 |
| `review`（check） | 检查失败或越出交付范围 | `failed` | |
| `review`（review） | 审阅通过 | `review`（merge） | |
| `review`（review） | 审阅退回，自动轮数没用完 | `queued` | `rework_count + 1`，新 Run |
| `review`（review） | 审阅退回，轮数或预算用完 | `blocked` | 进「待我处理」 |
| `review`（merge） | 候选提交冲突，或集成检查失败 | `blocked` | 集成分支不动 |
| `review`（merge） | 集成检查通过且分支推进成功 | `succeeded` | 放行下游 |
| `blocked` | 新计划版本确认 | 按新版本 | |
| 任何未结束状态 | 取消任务或节点被删 | `cancelled` | 先拿任务锁 |

### 检查、审阅、合并、崩溃恢复的时序

1. **提交**：`submit_result` 带 Run ID 和提交 SHA。服务先确认这次 Run 仍有提交资格：属于当前已确认的计划版本、节点修订号一致、没被取消。不满足的存档可查、标为「已作废」，不触发检查、合并或放行下游。
2. **检查**：在子任务 worktree 的这个 SHA 上跑检查命令，结果记下 SHA、命令和输出。
3. **审阅**（需要时）：审阅助手在只读会话里看这个 SHA 的 diff，意见绑定 SHA。
4. **合并**（持任务锁，同一任务串行）：
   1. 写 `merge_ops`：操作 ID、源 SHA、目标旧 HEAD，阶段 `started`。
   2. 在临时 worktree（从旧 HEAD 分离检出）里合并源 SHA，得到候选 SHA，阶段 `candidate`；冲突则中止，阶段 `conflict`，子任务 `blocked`。
   3. 在候选 SHA 上跑集成检查（已合入各子任务的检查命令合集，计划确认时一并确认）。
   4. 通过：`git update-ref` 把集成分支从旧 HEAD 推进到候选 SHA（旧值不符就失败，不覆盖）；随后在同一个数据库事务里把阶段改为 `done`、子任务 `succeeded`、写事件、放行下游。
   5. 失败：阶段 `check_failed`，集成分支不动，子任务 `blocked`。
5. **崩溃恢复**：启动时扫描没到 `done` / `conflict` / `check_failed` 的 `merge_ops`：
   - 集成分支等于候选 SHA：Git 已推进、数据库没落，补记 `done`，不重复合并。
   - 集成分支等于旧 HEAD：从头重做合并或复用候选提交，重跑集成检查。
   - 两者都不是：分支被别人动过，子任务 `blocked` 交给你处理。
   - 清理残留的临时 worktree。
6. **最终交付**：全部子任务 `succeeded` 后，在集成分支 HEAD 上跑一遍所有检查，结果绑定这个 SHA，再唤醒协调助手汇总。

以现有表为基础，新增：`agent_profiles`；`plans`（任务的计划版本、状态、确认人与时间；修改计划产生新版本）；`wakes`（触发类型、去重键、主会话、状态、请求次数）；`session_summaries`（滚动摘要，保留历史）；`auto_decisions`；`mcp_tokens`（Run ID、令牌哈希、角色、过期时间）。`merge_ops`（见上文时序）。`subtasks` 加计划版本、节点修订号、`gate_stage`、执行器、交付范围、检查命令、分支；`runs` 加计划版本和节点修订号（判断提交资格）；检查结果和审阅记录加提交 SHA；`tasks` 加集成分支。计划版本确认后不可修改。具体字段在实现第一项时写进架构文档再建表。

## 安全要点

- 编排工具的身份只来自令牌和 Run ID；令牌只在内存和子进程环境变量里，不进日志和数据库明文。
- 计划只是提议，执行前必须经用户确认（或明确打开的自动跳过并留记录）；外部消息产生的计划同样要确认。
- 专业助手之间的改动靠独立 worktree 分开；能写到哪里以执行器沙箱为准（P3-00 实测）。交付范围由验收闸门核对 diff，不当作隔离。
- 子进程环境变量白名单（Claude、Codex 都是），不把渠道凭据和其他执行器的凭据带进去。

## 验收

### 自动化（离线，进 CI）

用模拟 Codex + 模拟 Claude 跑：

1. 开发 → 测试 → 文档 → 汇总的三段依赖，两种执行器混用，最终集成分支包含三个子任务的提交。
2. 依赖失败：开发失败，测试和文档进入 `blocked`，协调助手被唤醒并提出修改计划，确认后重跑通过。
3. 审批超时：测试助手的审批 30 分钟（测试里缩短）无人处理被拒，子任务按结果失败，下游阻塞。
4. 取消：运行中取消任务，所有 Run 停止、未开始的子任务 `cancelled`，没有残留进程（mock 层面）。
5. 冲突：两个并行子任务改同一行，后合并的进入 `blocked`，解决冲突子任务完成后继续。
6. 重启恢复：在每个关键状态（执行中、等待审批、候选提交检查中、汇总中）杀掉服务后重启，状态一致、不重复派单、不重复回复。
7. 验收闸门：模型声称通过但检查命令失败 → `failed`；改动越出交付范围 → `failed`。
8. MCP 桥：错误令牌、过期令牌、专业助手调用协调工具一律拒绝并审计。
9. 集成检查失败后再派单：子任务 A 的候选提交集成检查失败，集成分支停在上一个通过的 HEAD，A `blocked`、下游不派发；修改计划后新派的 worktree 基于上一个通过的 HEAD。
10. 删节点后旧 Run 迟到提交：运行中删掉节点 X 并确认新版本，X 的 Run 在取消信号之后才 `submit_result`，结果存档并标为「已作废」，不触发合并或放行下游。
11. 合并崩溃窗口：在分支推进成功、数据库还没落时杀掉服务，重启后补记完成，不重复合并、不重复放行。
12. 返工上限：审阅助手连续退回，第 2 轮后再退回就转 `blocked` 等用户；用户手动退回不受限。
13. 计划编辑校验：删掉前置节点留下悬空依赖、换成实测不支持只读的执行器去当审阅，确认都被拒并提示原因。
