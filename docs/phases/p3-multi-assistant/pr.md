# P3 多助手协作：变更说明

分支 `claude/p3-multi-assistant`，基于 master `fc49e0c`（P2 已合入）。尚未推送，也未开 PR（推送由 Willem 本人做）。计划见 [P3 开发计划](plan.md)（2026-11-25 批准的第二版，各工作项的「实现要点」写在对应小节里），实测见 [P3 实测记录](findings.md)，需要你本人走一遍的项目见 [实测清单](checklist.md)。

## 前因

P2 让人在手机上也能给 PalDock 派活，但始终只有「一个任务一个开发助手」：外部消息一律当成新任务目标，没有人帮你拆任务、协调、汇总。P3 的目标是路线图里的「多助手协作」：你对协调助手说一个目标，它提出带依赖的计划；你确认后，调度器把子任务派给不同执行器上的专业助手（Claude 开发、Codex 测试和审阅……），每个写入型子任务在自己的 worktree 里做，交付后由服务自己验收、审阅、合进任务集成分支，最后协调助手汇总回到发起的地方。你只做三件事：确认计划、处理审批、把集成分支合进自己的分支。

范围按 2026-11-25 已定的几点：只做「项目协作」一种模式；模式、触发器、长期记忆和向量检索放到 P3 之后；Claude 用 CLI 接入；合进你真正的分支永远由你自己做；计划在对话里确认，简单计划自动确认（2026-11-26 取代 11-25 的「每个计划都要确认」）。

## 实现方案（按工作项）

**分包**：新增的都在已有包里，依赖方向不变（`apps/local-service → application → domain → contracts`，`storage-sqlite` 实现 contracts 的存储接口）。application 里新增 `task-graph-scheduler`、`plan-service`、`review-gate`、`integration`、`coordinator`、`recovery-service`；它们都按事件驱动，事件由本地服务在事务提交后统一分发，各自在下一个微任务里处理（共用 `util.ts` 的 `MicroBatch`），不在产生事件的事务里写库。

- **P3-03 MCP 桥**：每次 Run 签发一次性令牌（只存 sha256、只在内存，Run 结束即作废），桥脚本经本机 IPC 连回服务；工具按角色列出：协调助手 `propose_plan` / `get_status` / `notify_user` / `write_summary`，专业助手 `get_task` / `submit_result`，审阅助手另有 `submit_review`。没有任何写文件的工具（MCP 服务进程在执行器沙箱外）。
- **P3-04 任务图**：`plans`（每版一行，`revision` + 乐观 `version`）、`plan_nodes`；domain 的 `validatePlan`（≤8 节点、角色存在、无环、项目内路径）、`graphStep`（放行 / 链式阻塞 / 上游恢复后解除）、`taskStatusOf`（任务状态由子任务推导，单子任务和任务图同一条规则）。并发：全局 10、每任务 4、同一会话串行。
- **P3-05 验收与审阅**：节点交付即提交到节点分支，核对交付范围（角色范围 ∪ 节点路径），跑节点的检查命令（随计划确认）；越界或检查失败交给你；可写角色的节点交给审阅助手（每轮新的独立会话、只读），经 `submit_review` 交结论；自动退回最多 2 轮。
- **P3-06 集成分支**：计划确认时从项目 HEAD 建 `paldock/<任务编号>`；节点通过后在临时 worktree 出候选合并提交、跑集成检查，通过才快进集成分支；冲突或集成检查失败时分支不动、交给你（交回开发助手重做，或人工处理后重试）；`merge_ops` 先写后做。下游节点从集成分支建 worktree。可选的「worktree 准备命令」解决新 worktree 没装依赖的问题。
- **P3-07 主会话**：协调助手的 Run 挂在一个隐藏的「对话任务」上（`tasks.kind = 'conversation'`），在项目根目录只读运行；唤醒循环（你的消息、节点阻塞或交给人、任务全部通过、计划退回、审批被拒）带频率限制（2 分钟间隔、每天 20 次）和请求上限（20 / 40，按 MCP 工具调用计数）；`notify_user` 先桌面后按审批升级规则外发；`write_summary` 滚动摘要（最小版）。
- **P3-08**：确认前改执行器、检查命令、删节点；确认 / 退回都可带意见并交给协调助手；运行中确认新一版（没变的沿用、改了的连同下游重做、删掉的取消）；按项目、按角色跳过审阅；`auto_decisions` 记所有没经过你的决定。
- **P3-09 重启恢复**：存储层先中断没结束的工作，恢复程序再收拾 P3 的中间状态：节点的 Run 按 `checkTurn` 补记 / 记失败 / 续做，审阅用新会话重审，合并按 `merge_ops` 补记 / 重做 / 交给人并清残留，唤醒放回队列，调度器再推进；「待我处理」顶部列出本次恢复了什么。
- **P3-10 外部消息**：普通文字进这个外部会话对应的主会话，命令照旧；Q 编号问题的回复按引用回复、编号开头、唯一待答问题三种方式交回提问方，拿不准时交给协调助手；协调助手的回复和完成汇总经 outbox 发回；计划确认卡片（L0 不发、L1 只确认不带检查命令的、L2 都能，先到者为准）。
- **P3-11**：真实执行器端到端实测脚本 `tests/live/p3.live.test.ts`（本地服务跑在子进程里，可以真的强杀）。完整链路、强杀重启、冲突三个场景用真实 Codex + Claude 各成功跑一次，结果、用时、用量见 [findings.md](findings.md)。实测发现并修了四个问题（都补了离线测试）：父进程被杀后服务成孤儿进程；Claude 每次改文件都来要审批（改为 worktree 内的文件改动由宿主直接批准并审计，2026-11-25 的决定）；设置填 `codex.cmd` 时 Codex 起不来；Codex 用量没记到 Run 上。

## 偏离计划的地方和理由

| 计划 | 实际 | 理由 |
|---|---|---|
| `mcp_tokens` 表 | 令牌只放内存 | 服务重启时所有 Run 都已中断，旧令牌本来就该作废，落库反而多一处要清理的凭据（迁移 006 注释） |
| 越界 / 检查失败 / 冲突 → `failed` 或 `blocked` | 停在待验收、交给你 | `failed` 在没有运行中改计划之前是死路；交给人才能在桌面上人工通过、退回或重做 |
| 自动退回「不设上限」（P3-05 说明） | 最多 2 轮，人工退回不限 | 按已批准的计划 v2「返工的终止条件」，防止两个助手来回退回空耗额度；常量可改 |
| 「简单任务可跳过计划确认」 | 先不做（11-25），2026-11-26 改为：对话页里直接确认；简单计划（新任务、1 个节点、不带检查命令）30 秒后自动确认，期间可撤回，按项目开关、默认开 | 你实测时发现每个计划都得进任务页确认很麻烦；多节点或带检查命令的仍要你确认。等 30 秒是为了让撤回来得及（确认后节点立刻开始）。迁移 014：计划记排定时间，`auto_decisions` 加两种决定 |
| 合进你的分支 | P3 不做，显示「待合并」 | 已定的几点第 4 条，2026-11-25 再次确认 |
| 主会话用独立表 | 挂在隐藏的「对话任务」上 | Run 必须挂在子任务上；改成按会话的执行器是大重构，记为后续（见下） |
| 单次唤醒「模型请求」上限 | 按 MCP 工具调用计数 | CLI 执行器看不到每一次模型请求，这是能拿到的最接近的计数 |
| `channel-desktop` / `channel-mock` 两个包 | 不做 | 桌面对话直接走主会话，测试用 P2 的假适配器；等真的有第三种渠道再抽 |
| 单子任务（P1 / P2）的自动恢复 | 仍由你手动恢复 | 保持 P1「排队只在内存里，重启后不自动继续」的约定；只有计划节点自动恢复 |
| 每次写文件、跑命令都经审批 | 写自己 worktree 里的文件、Claude 在 worktree 内跑的普通命令由宿主直接批准，记 `approval.auto` 审计 | 2026-11-25、11-26 你定的：Windows 可写角色「不隔离」、不逐条审批；Codex 沙箱本来就不问，这样两种执行器一致。安装依赖、git push / merge / rebase / reset、网络下载、涉及 worktree 外的命令、大范围删除、权限扩展照旧审批（plan.md「已定的几点」第 10 条；规则是 domain 的 `classifyCommand` / `isAutoApproved`，有单测） |

## 自查：`/code-review` 与 `/simplify`

**`/code-review`（high，master...HEAD）10 条，全部采纳**：

1. 运行中改计划后，被替换节点的新子任务落进旧 worktree 和分支 → 新版本建的子任务 slug 带 `-r<版本>`（补测试）。
2. 合并时 git 出非冲突错误只记日志、节点卡住 → 操作记失败、交给人（补测试：集成 worktree 有挡路的未跟踪文件）。
3. 重启恢复中途一项出错就中断整个恢复 → 每项单独兜底，唤醒最先放回队列。
4. 等频率间隔的任务事件唤醒挡住你的消息 → 先处理排在后面的用户消息（补测试）。
5. `PALDOCK_LIVE_CODEX=1` 会顺带跑 P3 实测、白耗额度 → 两个实测各按自己的环境变量开关。
6. 对话页选项目出错后立即重绘、错误提示被冲掉 → 出错时不重绘。
7. `get_status` 返回其他项目的任务 → 只返回调用方所在项目的（补测试）。
8. 协调助手的任务板先取全局再筛项目、可能漏掉 → 按项目查。
9. 启动清理按项目重复查任务列表 → 只查一遍（后来又改为只看没结束的计划任务）。
10. `workspace.add` 借用建任务的路径 → 直接校验后登记。

**`/simplify`（复用、简化、效率、深度四个角度，共 37 条，去重后约 25 条）**：

采纳（已改）：
- 三个服务各写一遍的微任务批处理 → `MicroBatch`；四份 `errorText` → 一份。
- 「过闸门 → 子任务成功 → 推导任务状态」 → `succeedSubtask`；ReviewGate 的 `integration` 改为必填，只剩合并这一条成功路径（没有集成分支的任务由合并服务直接记成功）。
- 节点标题、交接摘要、主会话查找、执行器解析、任务短编号各合成一个辅助函数（`nodeTitle`、`handoffOf`、`mainSessionOfRun`、`executorOfRole`、`taskRef` 移到 domain）；`send` 和 `receiveExternal` 合成 `ingest`；删掉没用的常量，终态判断用状态机；`integration.redo` 用 `requireSubtask`；计划存储复用 `TaskRepository.getTask`；协调存储用 `insertWithEvent`；集成检查合成一个循环。
- 效率：按 `(plan_id, node_key)` 单查节点；计划详情不读输出正文、闸门数据取自同一份 `runDetails`；重启恢复用专门的查询（审阅中的节点、有确认计划且没结束的任务）代替扫 500 个任务；清理合并残留先看 `MERGE_HEAD` 文件；对话页少一次请求。

不采纳（记为后续）：
- **监管器改成按会话的执行器、用完成回调代替模式分支和「对话任务」**（深度 1、2、6）：根因判断是对的，但要改 `runs.subtask_id`、监管器、协调、审阅和迁移 011，属于大重构；P3 先保持现状，作为 P3 之后的第一项技术债。
- **任务状态改成纯投影**（深度 3）、**单子任务建成一节点计划**（深度 4）、**各模块注册恢复钩子、存储层不再一律阻塞**（深度 8）：都会改动 P1 / P2 已有的语义和测试，单独一轮做。
- **每次启动 Run 都重新探测执行器**（效率 1）：P3-02 有意这么定的（能及时发现执行器被卸载、登出、升级），保留。
- **事件载荷加路由字段**（效率 7）：要改事件契约，现在的额外读都是主键查询，收益小。
- **调度一次推进里多个节点各自重读计划**（效率 9）：一个计划最多 8 个节点，收益小。

## 0.3.x 实测后的改动

- **0.3.1**：界面停在「本地服务启动中」——对话页从共享包导入了值，渲染进程没有打包器；加了测试禁止。
- **0.3.2**：对话里确认计划、简单计划自动确认（30 秒内可撤回）；「待我处理」和任务页直接处理审批。
- **0.3.3**：原生会话复用（plan.md 第 12 节）。协调助手不再每轮重发角色说明和任务板；专业助手按（项目，角色，执行器）复用原生会话，每轮切到节点的 worktree，审阅单独成池，并行用会话池（大小 = 角色并发上限），跑满 30 轮或 400 万 token 后先写角色摘要再换新会话，换下的 Codex 会话归档；续用失败时换新会话重试。迁移 015（`role_sessions`、`runs.role_session_id`）。`write_summary` 对专业助手开放（写角色摘要）。
- **0.3.4**：项目级助手设置（plan.md 第 13 节）。新增「项目」页，按项目设置工作模式（团队 / 单人）、启用的角色、每个角色的执行器、隔离方式（独立 worktree / 直接在项目目录里改 / 只读）、审批严格度（工作目录内自动批准 / 每条都审批 / 只审批高风险）、跳过审阅；简单计划自动确认、准备命令、远程审批等级从设置页挪到这里。单人模式让对话页的主会话获得写权限（不新建角色），可选改完让审阅助手看一遍。只读角色现在真的用 Codex 的只读沙箱（以前审阅助手也是可写沙箱）。迁移 016（`project_agent_settings`、`project_role_settings`）。已知限制：直接在项目目录里改的节点不提交、不进集成分支，同一计划里用 worktree 的节点看不到它还没提交的改动；交付核对以开始时工作区里已有改动为基线，同一文件你自己也改过时分不开。

## 已知限制

- Windows 上可写角色不能限定目录（P3-00 实测），只在验收时核对交付范围，标「不隔离」。
- 命令分类只看命令文本，按关键字归类（宁可多问一次）：例如 commit 信息里出现「push」也会被当成 push 去审批；通过变量、脚本文件间接执行的操作看不出来，靠 worktree 和验收时的交付范围核对兜底。
- 检查命令和准备命令以你的账户权限运行、可以联网；准备命令的产物必须在项目的 `.gitignore` 里。
- 「只有一个待答问题时直接回复就算答复」可能把无关的话当成答复，实测后如果太激进可以收紧为只认引用回复和 Q 编号。
- 计划卡片只能确认或退回，修改还要回桌面；渠道里的任务图入口（/status 看节点等）没做。
- 协调助手的「请求上限」是按工具调用的近似。
- 滚动摘要是最小版，没有长期记忆和分层。
- macOS 上的只读与目录限制没有实测（Mac 测试包下一版加）。
