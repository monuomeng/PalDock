# ADR 0001：本地优先、契约驱动的桌面助手架构

状态：提议，2026-11-17。P0 完成后复核；不是已验证的实现承诺。2026-11-20 起，进程形态、编排方式、审批路由、存储、首批渠道和平台范围由 [ADR 0002](0002-process-topology-and-task-board.md) 细化。

## 背景

产品需要 Windows 桌面、多个渠道、独立助手会话，以及本地 Codex/Claude 能力。供应商会话语义和审批机制不一致，外部消息不能直接等同于本机执行权限。

## 决策

拟采用 Electron + TypeScript 桌面前端，本地应用服务和 SQLite；渠道和执行器作为可替换适配器，以版本化契约和领域状态机连接。核心服务管理任务、会话、授权、审计及持久化。桌宠作为 UI，与后台执行解耦；以用户显式设置决定是否常驻。

Codex 优先验证官方 app-server；Claude 优先验证官方 SDK / CLI；飞书优先验证官方长连接。只在这些接口无法满足且授权允许时研究可选观测探针。Higress 作为可选模型接口，不假设可接管供应商订阅或代理所有协议。

## 理由和代价

Electron/TS 便于共享协议模型、构建 Windows 桌面、实现长连接，但内存占用和权限边界需要实测。SQLite 易于单机交付，但并发、迁移和故障恢复需验证。独立适配器增加设计成本，换取供应商替换和错误隔离。

## 未决验证

P0 验证原生运行时版本/认证/审批与恢复、模型能力、飞书权限、桌面隔离、安装路径与备份。Claude 是否可用、桌宠引擎、通知/后台策略、开源许可证以及 IM 首选渠道均未决定。若实验失败，记录证据并提出替代 ADR。
