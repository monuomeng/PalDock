# 桌宠统筹与助手会话设计

状态：设计提议，2026-11-17；2026-11-20 按 [ADR 0002](adr/0002-process-topology-and-task-board.md) 更新。不是已实现或已验证的功能。

## 产品目标

用户从桌面或已授权的外部渠道向个人助手交代目标；个人助手理解并提出计划，按权限创建、继续和管理多个助手会话，跟踪任务、审批、失败和结果。桌宠显示状态，任务系统保存事实并执行确定性规则；桌宠外观或某个模型会话退出，不应导致任务凭空消失。

```text
用户（桌面 / 飞书等）
    → PalDock 主会话（协调助手）
        → 结构化计划 / 任务与依赖
            → 开发助手：PalDock 助手会话 → Codex 原生 thread
            → 测试助手：PalDock 助手会话 → Claude 原生 session
            → 文档助手：PalDock 助手会话 → 独立执行器会话
        ← 进度、审批、证据、结果、失败
    ← 桌宠通知 / 外部渠道回复 / 任务中心
```

以上是目标架构；外部平台、桌宠、各执行器的具体能力均需各自验证。

## 四层会话，不要混为一谈

1. **外部会话**：飞书群、单聊或桌面聊天；保存来源账号、用户、群和话题。多个来源默认不合并，需要用户显式绑定。
2. **PalDock 主会话**：个人助手与用户的持续交互；持久关联身份、来源、授权及任务，但不默认拥有全部项目权限。
3. **PalDock 助手会话**：为专业助手分配的长期或任务专属工作单元，由 PalDock 创建并维护 `parent_id`、助手、任务、范围和状态；可映射不同执行器。
4. **运行时原生会话或子代理**：Codex thread、Claude session，以及其内部自行创建的 subagent/team。能否创建、观察、恢复和继续由对应版本的官方能力决定；不把内部子代理误写为 PalDock 可永久控制的顶层会话，也不保证自动出现在其他桌面应用。

PalDock 的任务、会话关系和权限是系统记录；模型根据请求提出计划和使用受控工具，由确定性的应用服务验证并执行。复杂编排不能只依赖提示词或短期上下文。

## 对比与选型

Codex app-server 官方文档提供 thread 创建、turn、事件、审批等接口；Codex 的子代理能力另有文档，但具体本地版本、配置、事件可见性与生命周期必须在 P0 实测，不能将 OpenAI 托管 Agents API 的行为等同本地 app-server。[Codex App Server](https://developers.openai.com/codex/app-server)、[Codex Subagents](https://developers.openai.com/codex/multi-agent)。

Claude Code 支持独立上下文 subagent；Agent Teams 支持多个 Claude Code 实例、共享任务和通信，官方文档将其列为实验能力。其本地 CLI、Agent SDK 和云端 Managed Agents 是不同产品面，权限和恢复语义不能互相推导。[Claude subagents](https://code.claude.com/docs/en/sub-agents)、[Claude Agent Teams](https://code.claude.com/docs/en/agent-teams)。

不预设 Claude 或 Codex 在任务管理上必然更强；从原生文档看二者的组织形式不同。对 PalDock 分别评估多会话建立/恢复、事件可见性、审批、停止、交接、稳定性、费用与用户体验。PalDock 自有编排应支持二者，原生子代理是可选优化，避免双层编排造成重复分派。

## 协调能力边界

协调助手负责项目总览，PalDock 不对它的工具和具体实现方式做额外约束：它可以自己动手，也可以派单；但仍受项目授权、远程审批等级和审计约束，任务状态由调度器按事件推进。编排工具经每次 Run 注入的本机 MCP 桥提供，身份由令牌和 Run ID 确定，详见 [架构](02-architecture.md)「助手间编排」。

协调助手工具建议：`propose_plan`、`create_task`、`create_agent_session`、`assign_subtask`、`get_status`、`send_followup`、`request_approval`、`cancel`、`submit_result`；这些仅为规划中的应用内部能力，并非供应商现有命令。

每个工具必须验证调用者身份、任务来源、项目范围、助手能力、预算、并发限额和审批状态；工具结果返回结构化状态与可追踪 ID。会话状态由事件和进程状态共同确定，不能依据模型一句“已完成”推进为成功。任务与执行器状态分离；进程断开标记 unknown/interrupted，通过原生 ID 查询或人工核验后恢复，外部副作用不可盲目重放。

## 审批、上下文与监督

桌宠的授权/协作边界是 PalDock policy，不是模型自我约束。任务分配时传入最小必要上下文、目标、验收标准、允许目录及工具、预算和截止条件；不默认复制外部密钥和全部聊天记录。规划、执行、审核各自可见，并保留可审计的状态变更；禁止将不可信外部内容当成新的系统授权。

任务页显示来源、计划、子任务及依赖、负责人、运行时、时间、等待原因、审批、产物、可复现验证与费用估算；用户可查看、取消、补充要求和在安全边界内恢复。支持自动汇报时，必须通过授权渠道与身份；发消息前经过明确的产品授权策略。

## 首版验收建议

1. 主会话从本地请求创建一个有清晰职责和受控目录的 Codex 助手会话；流式回显、等待审批、拒绝、取消、结果均可见。
2. 退出 UI 后由用户选择后台继续或停止；重启后能查看任务并验证会话恢复，无法恢复时保留明确错误，不重复外部副作用。
3. 模拟第二执行器先使用 mock，验证异构会话映射、失败、任务依赖和去重；Claude 能力待安装/授权后用 opt-in 测试验证。
4. 测量协调质量：规定样例集，统计成功率、任务完成时间、成本、人工审批次数、错误分派/权限违规及会话恢复率；与单助手基线比较。

## 重要开放问题

各角色（含主协调者）的执行器都由用户自选，可配置使用 Claude、Codex 或普通模型，不预先绑定一家；先实现一个后加同一契约下的另一种并比较。需要确定普通任务是否默认自动建子会话、最大并发/成本预算、桌面关闭策略、什么时候经外部渠道推送以及谁有权审批。
