# P2 开发计划：外部渠道（飞书、Telegram）

状态：**第一版，用户已批准（2026-11-24），代码完成，待实机验收**。实现与偏差见 [变更说明](../pr/p2-external-channels.md)、[P2 实测记录](../p2/findings.md)。文末三点按计划所写执行；推送暂停，P2 全部完成后统一推送。负责人：Claude；分支 `claude/p2-external-channels`，基于 master（`ea2ee8f`，P1 已合入）。设计依据见 [架构](../02-architecture.md)「聊天渠道适配器」「审批路由与远程审批等级」、[ADR 0002](../adr/0002-process-topology-and-task-board.md)、[路线图](../03-roadmap.md)、[P0 实测记录](../p0/findings.md) 和 [P1 实测记录](../p1/findings.md)；完成后的前因后果写在 `docs/pr/p2-external-channels.md`。

## 目标

用户不在电脑前时，能在手机上通过飞书（之后是 Telegram）单聊和电脑上的 PalDock 打交道：查看任务、用一句话新建任务、收到结果和阻塞通知、在允许的风险范围内处理审批。电脑上的 PalDock 仍是唯一的事实来源，外部渠道只是入口。

退出条件（路线图 P2）：在测试租户里跑通消息接收、身份绑定与群白名单、会话路由、去重、断线重连、审批关联；未授权来源被拒绝并留审计。

## 已定的范围（2026-11-24，用户同意按建议）

1. **P2 只做外部渠道**。架构里挂在 P2 的项目监管模式、沟通模式、向量检索（sqlite-vec + bge-small-zh）移到 P3 前后再排。
2. **外部消息只走确定性命令和「消息即任务目标」**，不在 P2 做主会话或协调助手（仍在 P3）。外部文本一律当作不可信内容，只能作为新任务的目标，不能改设置、不能授权。
3. **先飞书，Telegram 跟进**：飞书做完并实测后再接 Telegram，Telegram 同时用来检验渠道契约是否通用。
4. **只做单聊**；白名单群聊放在最后一项，时间不够可以移出 P2。
5. **审批升级等待 3 分钟**，风险分级沿用 `packages/domain/src/approval-policy.ts` 现有草案。
6. **Codex 最低版本先锁 0.166**：低于此版本拒绝启动并提示升级；更低版本以后有需要再测。
7. **任务提醒模式不进 P2**（我的建议，**待你确认**，见文末）。

## P2 的范围取舍

为了先把「手机 ↔ 电脑」这条链路打通，下面几处有意简化：

1. **只有一个用户**。数据库里建一个「本机所有者」Principal，所有绑定都挂在它下面；多人、角色、共享审批以后再说。
2. **外部只能新建任务、看状态、取消、审批、验收/退回**；建任务时没有检查命令（检查命令需要在桌面确认，P1 的规则不变），需要时到桌面补。
3. **服务仍随界面退出**（托盘常驻在 P4）。所以「桌面 UI 未运行」这个升级条件在 P2 不会出现：界面关了，服务和渠道也都停了。电脑睡眠时服务也不运行，审批不会被送出；这两点在界面和文档里写明。
4. **渠道凭据由用户在设置页填入**，存进系统凭据库（Windows 凭据管理器、macOS 钥匙串），不落盘、不进日志。

### 1. P2-01 渠道契约与公共管线

- **契约**（`packages/contracts`）：`ChannelAdapter`（`start` / `stop` / `send` / `edit` / 状态事件）、`InboundMessage`（平台、租户、会话、线程、发送人、文本、引用、卡片动作）、`OutboundMessage`（文本或卡片、关联的业务对象）。适配器只做协议转换；身份、准入、路由都在公共管线里。
- **入站**：适配器收到事件后只调一次 `Inbox.accept`（已有，主键 `(queue, event_id)`，墓碑去重），队列名为 `provider:account`。一个入站工作器按会话串行领取（已有 `claim` 的租约逻辑），依次做归一化 → 身份解析 → 准入 → 路由 → 分类，每一步失败都以 `rejected` 结束并写审计事件。
- **出站**：业务代码只往 outbox 写记录，与状态变更同一事务（表已有）。投递工作器按渠道限速、重试（指数退避，占位最多 5 次）；发送超时记为 `unknown`，不盲目重发。卡片需要后续更新时，把平台返回的消息 ID 记在投递记录上。
- **桌面也走同一条管线**：`channel-desktop` 先做最小实现（P1 的界面命令不改），保证契约在两种渠道上都能跑；`channel-mock` 给测试和 CI 用。
- **迁移 003**：见下文「数据」。

### 2. P2-02 身份绑定与配对码

- 陌生人在单聊发任何消息，机器人只回一个 8 位一次性配对码（1 小时过期，每个渠道账号最多 3 个待处理请求），不回其他内容。
- 用户在桌面「设置 → 渠道 → 待绑定」看到渠道、对方显示名和配对码，确认后才绑定；可随时解绑（解绑后该账号的消息一律拒绝，未处理的远程审批卡片失效）。
- 绑定只授予单聊权限。群聊另需白名单（P2-08）。
- 未绑定账号的消息除配对外一律拒绝并记审计；同一账号短时间内大量请求按限速丢弃（占位每分钟 10 条）。

### 3. P2-03 凭据与渠道设置

- `packages/platform` 补写入和删除：Windows 用 CredWrite / CredDelete（与 P0 的 CredRead 同一方式），macOS 用钥匙串（`security add-generic-password` / `find-generic-password`，秘密经 stdin 传，不进命令行参数）。macOS 部分放进下一轮 Mac 测试包验证。
- 设置页「渠道」：填写飞书 App ID / App Secret、Telegram Bot Token、代理地址；启用/停用开关；连接状态（已连接、重连中、渠道刚恢复）。凭据只写不回显。
- 渠道启停不影响本地任务；某个渠道启动失败只在该渠道上显示错误。

### 4. P2-04 飞书单聊适配器

- 官方 SDK `@larksuiteoapi/node-sdk`（已锁 1.76.0，MIT）的 WSClient 长连接，订阅 `im.message.receive_v1` 和 `card.action.trigger`。`event_id` 作为去重键。
- 回复一律用交互卡片（只有卡片能更新）。任务进度类卡片按 500ms 节流更新同一张卡片，结束时更新一次终态；P2 不把执行器的流式输出逐字推到手机，只推关键节点（开始、等待审批、待验收、失败、完成）和最终回复摘要。
- 卡片按钮带一次性动作令牌（绑定审批 ID 和版本号），点击人必须是已绑定的 Principal；同一按钮重复点击只生效一次。
- **断线**：P0 实测断线期间的消息在恢复后约 314 秒才补投。重连后 6 分钟内，设置页和「待我处理」顶部显示「飞书刚恢复，消息可能延迟」；补投靠 `event_id` 去重。
- **待实测**：`card.action.trigger` 能否经长连接收到（P0 未测）。如果不行，备选为卡片上不放按钮，改用文字命令 `/approve <短码>`；实测结果写进 findings。
- **离线测试**：适配器内部分两层，协议转换是纯函数（真实事件样本做输入），网络层用假的 WSClient 注入；CI 不连飞书。

### 5. P2-05 外部命令与任务链路

确定性命令（以 `/` 开头，直接调应用服务，不经模型）：

| 命令 | 作用 |
|---|---|
| `/help` | 列出命令 |
| `/projects`、`/use <项目>` | 列出项目；设置这个会话的默认项目 |
| `/tasks` | 最近任务和状态（最多 10 条） |
| `/status <任务>` | 一个任务的状态、等待原因、最近一次 Run 摘要 |
| `/cancel <任务>` | 取消任务（卡片二次确认） |

- **消息即任务目标**：不以 `/` 开头的文本，回一张确认卡片「在 <默认项目> 新建任务：<目标>」，点确认后建任务并开始执行，与桌面建任务走同一个用例。没设默认项目时先提示 `/use`。
- **结果回到发起渠道**：从外部建的任务在任务上记 `origin_conversation_id`；该任务进入待验收、阻塞、失败、完成时，往发起会话发卡片。待验收卡片显示改动统计和最终回复摘要，可「验收」或「退回」（退回需要输入意见，用卡片输入框；不支持时改为回复文字）。
- 桌面建的任务不往外部推（普通通知桌面优先，架构已定）；审批升级例外，见下一项。

### 6. P2-06 桌面状态与审批升级

- **桌面状态来源**：Electron 主进程用 `powerMonitor` 维护「是否锁屏、是否空闲、是否即将睡眠」，状态变化时经已有 IPC 发给服务。按 P1 实测，Windows 上锁屏事件会重复，**只按状态变化发送**（已锁屏时再收到 lock-screen 忽略），并以 `getSystemIdleState` 的 `locked` 兜底。空闲阈值占位 5 分钟。
- **升级调度**：服务定时扫描 pending 审批（复用 `approvals_pending` 索引），对满足 `shouldEscalateApproval` 的审批写 `escalated_at` 并往已绑定的单聊发卡片。项目远程审批等级允许的风险级别给「批准 / 拒绝」按钮，不允许的只发「有一个审批等待你在桌面处理」。
- **先到者为准**：两端都按审批的 `version` 做条件更新，后到的一方得到「已在桌面/飞书处理」；处理后另一端的卡片或弹窗同步更新。`decided_via` 记录来源渠道和账号。
- **远程审批等级设置**：项目设置页加 L0 / L1 / L2 选择（只能在桌面改，默认 L1）；切到 L2 时二次确认并说明含高风险。
- 审批的过期时间（30 分钟）不变；升级后过期同样作废外部卡片。

### 7. P2-07 Telegram 单聊适配器

- Bot API 长轮询（`getUpdates`，`offset` 持久化在数据库），`update_id` 作为去重键；内联键盘 `callback_query` 对应卡片按钮，`editMessageText` 对应卡片更新。
- 用 Node 内置 `fetch`，不引入额外 SDK；代理经设置页配置（中国大陆需要）。
- 复用 P2-01 的契约测试，加一份 Telegram 的协议转换样本测试。
- **前提**：需要你提供测试 bot（BotFather 创建）和可用代理；没有的话这一项只做离线部分，实机验收标注阻塞。

### 8. P2-08 白名单群聊（可移出 P2）

- 群需在桌面加入白名单才响应；只响应 @机器人 的消息（@所有人 不算），Telegram 依赖 privacy mode。
- 群里只能用 `/tasks`、`/status` 和建任务，**不发审批、不能审批、不能取消**；群里建的任务结果回到群里。
- 发送人仍需是已绑定的 Principal，否则拒绝。

### 9. P2-09 P0/P1 遗留验证项

| 项 | 做法 |
|---|---|
| Codex 最低版本 | `discover` 解析 `--version`，低于 0.166.0 拒绝启动，界面提示升级 |
| 睡眠 / 唤醒（Windows） | 诊断开关下实测 `suspend` / `resume`，确认唤醒后渠道重连、审批升级计时正确 |
| 锁屏 / 空闲 / 睡眠（macOS） | 加进 Mac 测试包，连同钥匙串和 P1 端到端检查一起发出 |
| macOS 测试包结果 | 收回后写进 findings（目前 repo 里没有记录） |
| 服务被强杀后真实 Codex 是否残留 | opt-in 实测；若残留，启动时按 PID 清理遗留执行器进程 |
| Codex turn 中途崩溃的恢复 | opt-in 实测，对照 P1 用模拟执行器得到的行为 |

## 数据（迁移 003）

| 表 / 列 | 用途 |
|---|---|
| `principals` | 人类身份；P2 只有一行「本机所有者」 |
| `channel_accounts` | 平台账号，唯一键 `(provider, tenant_key, external_user_id)`，`principal_id` 为空表示未绑定，带 `status`（active / revoked） |
| `pairing_requests` | 配对码、渠道账号、过期时间、状态；部分索引只覆盖 pending |
| `external_conversations` | 唯一键 `(provider, account, tenant_key, chat_id, thread_key)`，类型（dm / group）、默认项目、群白名单标记 |
| `channel_cursors` | Telegram `offset` 等长轮询游标 |
| `delivery_refs` | 出站消息与平台消息 ID 的对应（卡片更新、审批卡片作废用），关联 outbox 记录和业务对象 |
| `tasks.origin_conversation_id` | 结果回发目标 |

查询条件与部分索引逐字一致、`RETURNING` 取回最新行，沿用 P0/P1 的约定，并用 `EXPLAIN QUERY PLAN` 测试固定。

## 安全要点

- 外部文本是不可信内容：只能成为任务目标，命令解析只认白名单命令，不从文本里解析出路径、权限或设置。
- 远程审批只在已绑定单聊进行；动作令牌一次性、绑定审批版本，过期或已处理的卡片点了无效。
- 日志和审计不写消息正文和凭据，只写平台、会话、事件 ID 和处理结果。
- 渠道被停用或凭据被删除时，未发出的 outbox 记录标为 failed，不在下次启用时补发。

## 验收

### 自动化（离线，进 CI）

- 管线：重复事件被拒、同会话串行、租约过期回收、未绑定拒绝、配对码过期与上限、解绑后拒绝。
- 出站：限速、重试、超时记 unknown 不重发、渠道停用后不补发。
- 审批升级：3 分钟、锁屏、空闲三种触发；L0 / L1 / L2 对不同风险的按钮；两端同时处理时只有一方成功；过期后卡片作废。
- 锁屏事件重复只产生一次状态变化。
- 飞书、Telegram 协议转换样本测试；命令解析；Codex 版本门槛。

### 实机（opt-in，用你的测试租户和 bot）

1. 陌生账号发消息 → 只收到配对码 → 桌面确认后绑定。
2. 单聊发目标 → 确认卡片 → 任务在桌面出现并执行 → 待验收卡片 → 手机上验收。
3. 断网 3 分钟再恢复：界面提示延迟，补投的消息不重复处理。
4. 审批：桌面 3 分钟不处理 → 飞书收到卡片 → 手机批准 → 桌面弹窗关闭；锁屏立即升级；L0 项目只收到提醒。
5. 已解绑账号、群里未 @、未在白名单的群，都被拒绝并有审计记录。
6. Telegram 重复 1–5 中适用的部分。

## 占位默认值（集中定义，后续可改）

升级等待 3 分钟；空闲阈值 5 分钟；配对码 1 小时过期、每账号 3 个待处理；入站限速每账号每分钟 10 条；出站重试最多 5 次；卡片节流 500ms；渠道恢复提示 6 分钟。放在 `packages/domain/src/defaults.ts`。

## 代码质量约定

沿用 P1：包边界清楚、方法简短、SQL 清晰并复用索引、保存后复用返回结果不回查；每项完成提交一次；最后跑 `/simplify` 和 `/code-review`，审阅意见逐条评估后再决定是否采纳。

## 不在本次范围

主会话与协调助手、项目监管和沟通模式、向量检索、任务提醒模式（待确认）、托盘常驻与开机自启、钉钉等其他渠道、iOS 客户端、附件收发、流式输出逐字推送到手机、多人与角色权限、代码签名。

## 需要你确认的几点（2026-11-24 已按此确认）

1. **任务提醒模式不进 P2**：它需要触发器和唤醒循环，与 P3 的主会话一起做更顺；如果你希望手机上先能设提醒，可以作为 P2 最后一项加入。
2. **外部建任务要不要每次弹确认卡片**：我建议要，防止误发的消息直接开始执行。
3. **Telegram 的测试 bot 和代理**：开始 P2-07 前需要你准备好；没有的话 Telegram 只做离线部分。申请步骤见 [申请 Telegram 测试 bot](../ops/telegram-bot.md)。
4. **推送**：本机不能 `git push`；按用户要求 P2 期间不推送，全部完成后统一给出推送命令。
